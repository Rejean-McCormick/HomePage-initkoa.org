000001 | # SenTient Architecture Blueprint
000002 | **Version:** 1.0.0-FINAL
000003 | **Status:** IMPLEMENTED
000004 | **Classification:** INTERNAL TECHNICAL REFERENCE
000005 |

000007 | 
000008 | ## 1. Executive Summary
000009 | **SenTient** is a next-generation Entity Reconciliation and Relation Extraction engine. It is designed to bridge the gap between messy, unstructured text and structured Knowledge Graphs (Wikidata/Wikibase).
000010 | 
000011 | It is not a monolithic application but a **Hybrid Orchestration System** that combines three distinct technological lineages into a single pipeline:
000012 | 1.  **Speed (Layer 1):** The FST-based rapid tagging of **OpenTapioca** (Solr).
000013 | 2.  **Semantics (Layer 2):** The context-aware NLP of **Falcon 2.0** (Python/Elastic).
000014 | 3.  **Structure (Layer 3):** The **Hybrid Memory** data modeling of **OpenRefine** (Java + DuckDB).
000015 | 
000016 | The goal is to achieve **High Precision (>0.85)** and **High Recall (>0.80)** on short-text queries while maintaining a sub-second response time for user interactivity.

000021 |

000001 | # Layer 1: Ingestion & Fast Tagging (The Sieve)
000002 | **Component:** `index_solr` + `core_java (Clustering)`  
000003 | **Technology:** Apache Solr 9.x (FST Tagger) + Java String Algorithms  
000004 | **Latency Budget:** < 50ms per batch
000005 | 
000006 | ---
000007 | 
000008 | ## 1. Overview
000009 | The **Ingestion Layer** is responsible for the initial intake of raw data and the high-speed identification of "Surface Forms" (substrings that resemble known entities).
000010 | 
000011 | **Philosophy:** "Fail Fast, Filter Early."
000012 | This layer does not attempt to understand context. Its only job is to reduce the infinite search space of text into a finite list of Candidate QIDs using strict string matching and pre-calculated popularity.
000013 | 
000014 | ---
000015 | 
000016 | ## 2. The Processing Pipeline
000017 | 
000018 | Data flows through this layer in three strict phases:
000019 | 
000020 | ### Phase A: Normalization & Fingerprinting (Client-Side / Java)
000021 | Before any network call is made to Solr, the Java Orchestrator performs local deduplication to reduce API load.
000022 | 
000023 | **The Algorithm (Key Collision):**
000024 | We utilize the **OpenRefine Fingerprint** method:
000025 | 1.  **Tokenize:** Split string by whitespace.
000026 | 2.  **Clean:** Remove punctuation and control characters.
000027 | 3.  **Lowercase:** Convert all tokens to lowercase.
000028 | 4.  **Sort:** Alphabetize the tokens.
000029 | 5.  **Deduplicate:** Remove duplicate tokens.
000030 | 6.  **Join:** Reassemble into a normalized string.
000031 | 
000032 | > **Example:**
000033 | > * Input 1: "The  University  of... Oxford."
000034 | > * Input 2: "Oxford, University of"
000035 | > * **Fingerprint (Both):** `of oxford university`
000036 | >
000037 | > *Result:* Both inputs map to the same Cache Key. We query Solr once, not twice.
000038 | 
000039 | ### Phase B: The FST Tagger (Server-Side / Solr)
000040 | We do not use standard Lucene text search (TF-IDF). We use the **Solr TaggerHandler**.
000041 | 
000042 | * **Mechanism:** The entire dictionary of Wikidata labels and aliases (~14M items) is compiled into a **Finite State Transducer (FST)** in memory.
000043 | * **Operation:** The raw text acts as a cursor traversing the FST graph.
000044 | * **Performance:** Lookup time is $O(k)$ where $k$ is the length of the input text, independent of the index size.
000045 | 
000046 | 
000047 | 
000048 | ### Phase C: The Authority Filter (Pruning)
000049 | Solr returns candidates. We immediately discard any candidate that:
000050 | 1.  Has a `popularity_score` < 100 (log-likelihood threshold).
000051 | 2.  Is a "Stop Word" entity (e.g., "The" -> Band "The", "To" -> TV Show "To") unless exact capitalization matches.
000052 | 
000053 | ---
000054 | 
000055 | ## 3. Configuration & Schemas
000056 | 
000057 | ### 3.1. Artificial Aliases (The OpenTapioca Strategy)
000058 | To make Solr "smart" without NLP, we inject metadata into the `text` field during the build process. This allows users to search by IDs as if they were names.
000059 | 
000060 | | Input Type | Raw Value | Indexed As (Solr `text`) | Resolved QID |
000061 | | :--- | :--- | :--- | :--- |
000062 | | **Label** | "Douglas Adams" | `douglas adams` | Q42 |
000063 | | **Twitter** | "@dna" | `@dna` | Q42 |
000064 | | **IMDb** | "nm0000726" | `nm0000726` | Q42 |
000065 | | **GRID ID** | "grid.4991.5" | `grid.4991.5` | Q42 |
000066 | 
000067 | ### 3.2. Solr Request Parameters
000068 | The Java Orchestrator must call Solr with these exact parameters to enable FST mode:
000069 | 
000070 | ```http
000071 | POST /solr/sentient-tapioca/tag?overlaps=NO_SUB&tagsLimit=5000&fl=id,label,popularity_score,types
000072 | Content-Type: text/plain
000073 | 
000074 | <Raw Text Body>

000001 | # Layer 2: The Semantic Linguist (Falcon 2.0)
000002 | 
000003 | **Component:** `nlp_falcon`  
000004 | **Technology:** Python 3.9+, Flask, ElasticSearch, SBERT (Sentence-BERT)  
000005 | **Latency Budget:** ~200ms per entity batch (Target) / 15s (Hard Limit)
000006 | 
000007 | ---
000008 | 
000009 | ## 1. Overview
000010 | 
000011 | While Layer 1 (Solr) finds strings that *look like* entities, **Layer 2 (The Linguist)** determines if they *make sense* in the current sentence.
000012 | 
000013 | **Philosophy:** "Context is King."  
000014 | This layer solves the "Paris Problem":
000015 | 
000016 | * Input: *"The Paris Hilton hotel is expensive."*
000017 | * Layer 1 sees: "Paris" (City? Person?), "Hilton" (Hotel? Person?).
000018 | * **Layer 2 decides:** The proximity of "hotel" vectors suggests "Paris" is a location/brand modifier, not the capital of France.
000019 | 
000020 | 
000021 | 
000022 | ---
000023 | 
000024 | ## 2. The Processing Pipeline
000025 | 
000026 | The Python service (`src/main.py`) executes a 3-step NLP pipeline for every "Ambiguous" batch received from the Java Core.
000027 | 
000028 | 
000029 | 
000030 | ### Phase A: The "Compression" (Stopwords & N-Grams)
000031 | 
000032 | Before expensive vector math, we clean the signal using the **Falcon Optimization**:
000033 | 
000034 | 1.  **Tokenization:** Split sentence into words.
000035 | 2.  **Stopword Pruning:** Remove non-semantic noise ("the", "is", "at") using `data/stopwords/falcon_extended_en.txt`.
000036 |     * *Note:* This list acts as a shared resource; users can update this file to filter domain-specific noise (e.g., "patient", "sample").
000037 | 3.  **N-Gram Generation:** Create sliding windows of tokens (size 1 to 6) to detect compound predicates (e.g., "Mayor of" -> `P6`).
000038 | 
000039 | ### Phase B: Property Extraction (The Edge Detector)
000040 | 
000041 | Uniquely, SenTient tries to find the **Relationship (Predicate)** before confirming the **Entity (Subject)**.
000042 | 
000043 | * **Mechanism:** The N-Grams are queried against the `sentient_properties_v1` ElasticSearch index.
000044 | * **Query:** Matches `label` (fuzzy) and `usage_count` (boost).
000045 | * **Result:** If we find "buried in" (P119), we boost candidate entities that are *Locations* (Q2221906) and penalize *People*.
000046 | 
000047 | ### Phase C: Contextual Vector Scoring (The SBERT Model)
000048 | 
000049 | This is the heavy lifting. We calculate the pure semantic distance between the user's row context and the candidate's Wikidata description.
000050 | 
000051 | 1.  **Embedding:** The context window (surrounding 5 words) is encoded into a 768-dimensional vector using `all-MiniLM-L6-v2`.
000052 | 2.  **Retrieval:** We fetch the pre-encoded description vectors of the candidates from ElasticSearch (`sentient_entities_fallback`).
000053 | 3.  **Cosine Similarity:**
000054 |     $$S_{Context} = \frac{A \cdot B}{\|A\| \|B\|}$$
000055 |     * Where $A$ is the input context vector and $B$ is the candidate description vector.
000056 |     * **Output:** A raw float between `0.0` (No relation) and `1.0` (Perfect semantic match).
000057 | 
000058 | 
000059 | 
000060 | > **Architectural Note:** This layer does **NOT** apply Levenshtein string distance penalties. That calculation is strictly reserved for the Java Core (Layer 3) to allow independent visualization of "Spelling vs. Meaning" in the UI. Ensure `ranking.levenshtein.enabled` is set to `false` in `falcon_settings.yaml`.
000061 | 
000062 | ---
000063 | 
000064 | ## 3. Data Integration (ElasticSearch)
000065 | 
000066 | Layer 2 relies on two specific indices in ElasticSearch.
000067 | 
000068 | ### 3.1. `sentient_properties_v1`
000069 | 
000070 | Stores Wikidata Properties (P-items).
000071 | 
000072 | * **Mapping:** defined in `config/elastic/falcon_mapping.json`.
000073 | * **Key Fields:**
000074 |     * `label`: "place of birth"
000075 |     * `expected_types`: ["Q5"] (indicates this property usually applies to humans).
000076 |     * `context_vector`: Dense Vector of the property description.
000077 | 
000078 | ### 3.2. `sentient_entities_fallback`
000079 | 
000080 | A partial mirror of Wikidata entities used *only* for re-ranking descriptions.
000081 | 
000082 | * **Why?** Solr (Layer 1) is optimized for IDs and Labels, not long text descriptions. Elastic holds the descriptions for vector comparison.
000083 | 
000084 | ---
000085 | 
000086 | ## 4. API Interface (Internal)
000087 | 
000088 | The Java Orchestrator talks to the Python Layer via REST.
000089 | 
000090 | **Endpoint:** `POST http://127.0.0.1:5005/api/v1/disambiguate`
000091 | 
000092 | **Request Payload:**
000093 | 
000094 | ```json
000095 | {
000096 |   "surface_form": "Paris",
000097 |   "context_window": ["Hilton", "hotel", "expensive"],
000098 |   "candidates": ["Q90", "Q47796", "Q167646"],
000099 |   "limit": 3
000100 | }

000001 | Here is the updated documentation for **Layer 3: The Core Orchestrator**.
000002 | 
000003 | I have refined the technical specifications to align with the "Split-State" architecture we discussed, ensuring the distinction between the in-memory grid (Instant Faceting) and the on-disk vectorized storage (DuckDB) is clear.
000004 | 
000005 | ---
000006 | 
000007 | #Layer 3: The Core Orchestrator (Java / OpenRefine Heritage)**Component:** `sentient_core`
000008 | **Technology:** Java 17, Jetty 10, Butterfly Framework
000009 | **Role:** State Management, API Gateway, and Final Adjudication
000010 | 
000011 | ---
000012 | 
000013 | ##1. OverviewThe **Core Layer** is the stable foundation upon which the experimental AI layers rest. It does not perform NLP; it performs **Management**.
000014 | 
000015 | **Philosophy:** "Hybrid Memory Architecture"
000016 | Unlike the original OpenRefine "Database in RAM" model—which hits a hard ceiling with large AI vectors—SenTient adopts a split-state strategy to handle the massive payloads generated by Falcon and Tapioca:
000017 | 
000018 | 1. **Hot Data (RAM):** Row IDs, Status flags (`JUDGED`, `PENDING`), and Raw text values. This preserves the **Instant Faceting** capability (< 10ms filtering) that users expect from OpenRefine.
000019 | 2. **Cold Data (DuckDB Sidecar):** Heavy AI payloads (Feature Vectors, Candidate descriptions, detailed Confidence Scores). These are "hydrated" (loaded) only when the user scrolls them into the Virtual DOM view or exports the data.
000020 | 
000021 | ---
000022 | 
000023 | ##2. The Butterfly ArchitectureSenTient retains the **Butterfly** modular framework to handle the HTTP lifecycle, acting as the bridge between the React frontend and the heavy AI containers.
000024 | 
000025 | ###2.1. The Servlet ModelThe entry point is `com.google.refine.RefineServlet`. It routes requests based on the Command Pattern, decoupling the UI from the processing logic.
000026 | 
000027 | * **Endpoint:** `http://localhost:3333/command/core/*`
000028 | * **Routing Logic:**
000029 | 1. **Frontend** sends `POST /command/core/reconcile`.
000030 | 2. **Butterfly** looks up the registered **Command** class (e.g., `ReconcileCommand`).
000031 | 3. **Command** validates the request and triggers a **Process** (`LongRunningProcess`).
000032 | 4. **Command** returns a JSON response `{"code": "ok", "jobID": "123"}` immediately, preventing UI blocking.
000033 | 
000034 | 
000035 | 
000036 | ###2.2. The Async Process ManagerBecause Layer 2 (Falcon) can take minutes to process large datasets (e.g., calculating vectors for 100k rows), the Core uses a **Non-Blocking** architecture.
000037 | 
000038 | * **Class:** `com.google.refine.process.ProcessManager`
000039 | * **Mechanism:**
000040 | * The `ProcessManager` maintains a priority queue of `LongRunningProcess` objects.
000041 | * It uses the `ThreadPoolExecutorAdapter` (configured in `butterfly.properties`) to allocate threads for API calls to OpenTapioca and Falcon.
000042 | * **Polling:** The Frontend polls `/command/core/get-processes` every 500ms to update the progress bar, ensuring the user is never left guessing.
000043 | 
000044 | 
000045 | 
000046 | ---
000047 | 
000048 | ##3. The Data Model (The "SmartCell" in Java)The most significant modification in SenTient is the extension of the `Cell` and `Recon` objects to support "Split-State" persistence.
000049 | 
000050 | ###3.1. The `Cell` ObjectLocated in `com.google.refine.model.Cell`.
000051 | It is the atomic unit of storage in the grid. In SenTient, it is polymorphic:
000052 | 
000053 | * **Raw State:** Contains only the `value` (String/Number).
000054 | * **Reconciled State:** Contains a pointer to a `recon` object.
000055 | 
000056 | ###3.2. The `EnhancedRecon` ObjectWe have extended the standard `Recon` class to support the **Consensus Score** and **Lazy Loading**. The heavy data is explicitly marked `transient` so it is not held in the Java Heap indefinitely.
000057 | 
000058 | **Fields added to Java Class:**
000059 | 
000060 | ```java
000061 | public class Recon {
000062 |     // --- Standard OpenRefine Fields (Kept in RAM) ---
000063 |     public long id;

000065 |     public Object [] features; // Lightweight feature flags
000066 |     
000067 |     // --- SenTient Extensions (Lazy Loaded from DuckDB Sidecar) ---
000068 |     
000069 |     // NOTE: These fields are transient. They are null by default and 
000070 |     // only hydrated by DuckDBStore.fetchVisibleRows() when the 
000071 |     // viewport requests them.
000072 |     
000073 |     public transient List<ReconCandidate> candidates;

000077 |

000080 | }
000081 | 
000082 | ```

000030 | ## 3. The SmartCell Core Object
000031 | 
000032 | The root container for all cell data.
000033 | 
000034 | ### `id`
000035 | * **Description:** Unique, random identifier assigned at creation. Used to map asynchronous NLP results back to the UI row.
000036 | * **Format:** UUID v4.
000037 | * **Nullable:** No.
000038 | 
000039 | ### `raw_value`
000040 | * **Description:** The original, immutable user input.
000041 | * **Source:** User Upload (CSV/Excel).
000042 | * **Note:** This field is **never** modified by the AI. We only modify the `reconciliation` object attached to it.
000043 | 
000044 | ### `fingerprint`
000045 | * **Description:** The "Key Collision" string used for local clustering.
000046 | * **Logic:** `lowercase(sort(tokenize(raw_value)))`.
000047 | * **Example:** "The Beatles" -> `beatles the`.
000048 | 
000049 | ### `status`
000050 | * **Description:** The current state of the cell in the lifecycle.
000051 | * **Allowed Values:**
000052 |     * `NEW`: No reconciliation attempted.
000053 |     * `PENDING`: Sent to Solr/Falcon, awaiting Async response.
000054 |     * `AMBIGUOUS`: Returned with multiple candidates (Score 0.40 - 0.85).
000055 |     * `MATCHED`: Confirmed link to a QID (Score > 0.85 or User Action).
000056 |     * `REVIEW_REQUIRED`: Auto-matched but flagged by Scrutinizers (QA Error).
000057 | 
000058 | ### `consensus_score`
000059 | * **Description:** The final calculated confidence.
000060 | * **Range:** `0.0` to `1.0`.
000061 | * **Calculation:** Computed in Java after receiving Python payload.
000062 | * **Critical:** If `null`, the UI displays "Processing...".

000075 | * **Type:** List of `Candidate` Objects.
000076 | * **Description:** The top $N$ suggestions (default 3) returned by the funnel.
000077 | * **Sort Order:** Descending by `consensus_score`.

This is the **Strategic Roadmap for the SenTient v1.1 Upgrade**.
