# EkoH Expertise Claims App — Alignment Brief

**Document ID:** `00-ekoh-expertise-claims-app-alignment.md`  
**Scope:** Environment alignment for the EkoH Expertise Claims app  
**Status:** Draft  
**Intended audience:** Product, architecture, governance, and development teams  

---

## 1. Purpose

This document defines the environment that the **EkoH Expertise Claims App** must align with inside Konnaxion.

The app is not a separate reputation system. It is **K-Port, the canonical EkoH evidence gateway**: a centralized intake and evidence-normalization layer that accepts user-submitted claims as well as source-authoritative evidence from trusted Konnaxion modules before admissible signals are handed to EkoH scoring.

The app fills a specific gap:

> EkoH already centralizes expertise scores, ethics scores, scoring parameters, privacy, and audit history, but it does not yet clearly define a centralized place for raw user-submitted expertise evidence or mark-of-merit claims.

---

## 2. Core alignment principle

The app must follow this principle:

```text
Evidence may come from anywhere in Konnaxion,
all EkoH-bound evidence passes through K-Port,
and reputation authority stays in EkoH.
```

Other Konnaxion modules may produce useful evidence:

- KonnectED may provide learning paths and portfolios.
- XKaliber may provide source-authoritative Caliber Profiles and observed competency results.
- CertifiKation may provide source-authoritative seals derived from confirmed XKaliber results.
- keenKonnect may provide project work, roles, resources, and reviews.
- Ethikos may provide debate contributions, arguments, and conduct signals.
- Smart Vote / Empower may provide community recognition signals.
- External sources may provide degrees, patents, publications, licenses, professional profiles, or institutional validation.

However, none of these modules should own the user’s canonical reputation profile.

That authority belongs to EkoH.

---

## 3. Existing EkoH environment

The app should align with the existing EkoH / Smart Vote environment.

### 3.1 Database context

| Item | Alignment target |
|---|---|
| Main database | Konnaxion PostgreSQL database |
| EkoH / Smart Vote schema | `ekoh_smartvote` |
| User identity source | Core Konnaxion user table / `auth_user` |
| EkoH module namespace | `konnaxion.ekoh` |
| EkoH app boundary | `modules/ekoh-smartvote/ekoh/` |
| Schema behavior | EkoH objects live under the EkoH / Smart Vote schema and reference the shared user table |

The Expertise Claims App should be treated as part of the EkoH module boundary, not as an independent Konnaxion module.

---

## 4. Existing EkoH objects to respect

The app must align with these existing EkoH concepts.

| Existing EkoH object | Role |
|---|---|
| `expertise_category` | Canonical expertise/domain catalogue |
| `user_expertise_score` | User’s current expertise score per domain |
| `user_ethics_score` | User’s ethical standing / trust multiplier |
| `score_configuration` | Tunable parameters used by the EkoH scoring engine |
| `context_analysis_log` | Explainable contextual or AI-assisted score adjustments |
| `confidentiality_setting` | User privacy level for score/profile visibility |
| `score_history` | Audit trail of score changes |

The Expertise Claims App should not replace any of these objects.

Instead, it should create a missing upstream layer:

```text
submitted claim / evidence
        ↓
verification and scoring process
        ↓
existing EkoH score and audit tables
```

---

## 5. The gap this app closes

EkoH is centralized around final score state and score history.

What is missing is a central intake structure for:

- user-submitted expertise claims;
- mark-of-merit evidence;
- supporting documents, URLs, certificates, and references;
- domain mapping for each claim;
- peer or expert validation of a claim;
- measurable impact attached to a claim;
- verification state before a score is changed;
- traceability from submitted proof to score update.

Without this layer, score changes can be audited after the fact, but the system lacks a clean central record of the original evidence that justified the change.

The Expertise Claims App should close this gap.

---

## 6. App role

The app should act as:

```text
EkoH's centralized claim and evidence intake layer.
```

It should allow users to submit structured claims such as:

- “I hold this degree or certification.”
- “I completed this project.”
- “I published this work.”
- “I created this educational resource.”
- “I contributed to this public-good outcome.”
- “I received this expert endorsement.”
- “I have measurable impact in this field.”
- “I have conduct or transparency signals relevant to ethical trust.”

The app should not allow users to directly assign themselves expertise scores.

Users submit evidence.  
EkoH evaluates evidence.  
EkoH updates scores.

---

## 7. Canonical merit dimensions

The app should align with EkoH’s merit model.

The main mark-of-merit dimensions are:

| Merit dimension | Meaning |
|---|---|
| Theoretical knowledge and qualifications | Degrees, certifications, research, patents, formal knowledge |
| Practical experience | Work history, field practice, hands-on achievements, project roles |
| Measurable impact | Quantified outcomes and real-world results |
| Peer recognition | Endorsements, reviews, citations, expert validation, community recognition |
| Knowledge dissemination | Teaching, mentoring, tutorials, documentation, open educational resources |
| Ethical integrity | Trustworthiness, conduct, transparency, conflict disclosure, respect for platform values |

These dimensions should be treated as the top-level claim categories.

Evidence types should sit underneath them.

---

## 8. Evidence sources

The app should support evidence from two broad source families.

### 8.1 Internal Konnaxion evidence

Examples:

- XKaliber Caliber Profile or confirmed assessment result;
- CertifiKation seal with status and validity metadata;
- KonnectED portfolio item;
- Knowledge resource;
- keenKonnect project;
- keenKonnect project role;
- project resource;
- project rating or review;
- Ethikos argument or debate contribution;
- Smart Vote / Empower endorsement;
- moderation or conduct signal;
- peer validation from another Konnaxion user.

### 8.2 Source-authoritative internal evidence

Trusted module evidence requires a different verification boundary from self-submitted evidence. For an XKaliber / CertifiKation record, K-Port should verify provenance, identity binding, status, expiry, scope, consent and domain mapping, but **must not re-run or re-score the assessment**.

The source module remains authoritative for the observed performance and confirmed level. K-Port is authoritative for admissibility into the EkoH evidence pipeline.

### 8.3 External evidence

Examples:

- academic degree;
- professional certification;
- license;
- publication;
- DOI;
- patent;
- portfolio website;
- GitHub repository;
- ORCID profile;
- professional profile;
- institutional verification;
- open badge;
- certificate ID;
- third-party registry entry.

The app should not assume all evidence is equally trustworthy.

It should distinguish between:

- self-attested evidence;
- peer-validated evidence;
- expert-validated evidence;
- institution-verified evidence;
- registry-verified evidence;
- API-verified evidence;
- blockchain-verified evidence;
- admin-reviewed evidence.

---

## 9. Relationship to EkoH scoring

The app should feed the EkoH scoring process, not bypass it.

A high-level flow should look like this:

```text
User submits expertise claim
        ↓
Claim is mapped to one or more expertise domains
        ↓
Evidence is attached or referenced
        ↓
Claim enters review / validation
        ↓
Verified claim becomes a scoring signal
        ↓
EkoH updates user_expertise_score and/or user_ethics_score
        ↓
Score change is recorded in score_history
        ↓
Contextual explanation is recorded where needed
```

The app should keep the distinction between:

| Concept | Meaning |
|---|---|
| Claim | A user-submitted statement of expertise or merit |
| Evidence | Proof supporting the claim |
| Validation | Review or confirmation of the evidence |
| Score signal | A verified input to the scoring engine |
| Score | The current EkoH result after scoring |
| Audit | The trace of why a score changed |

---

## 10. Boundary with other Konnaxion modules

Other modules may be evidence providers, but they should not become scoring authorities.

### Correct relationship

```text
XKaliber / CertifiKation / KonnectED / keenKonnect / Ethikos / Smart Vote
        ↓
evidence or source-authoritative proof
        ↓
K-Port — canonical evidence gateway
        ↓
admissible scoring signal
        ↓
EkoH scoring engine
        ↓
EkoH scores and audit trail
```

### Incorrect relationship

```text
Each module creates and owns its own expertise score, or sends a competency result directly into EkoH while bypassing K-Port.
```

The app must reinforce centralization in EkoH.

---

## 11. Privacy alignment

The app must respect EkoH privacy expectations.

Claims and evidence may contain sensitive information, such as:

- identity documents;
- degree records;
- employment history;
- professional licenses;
- institutional contacts;
- peer validator comments;
- ethics or moderation-related data.

The app should align with EkoH privacy levels:

| Privacy level | Meaning |
|---|---|
| `public` | Claim or score may be publicly associated with the user |
| `pseudonym` | Claim or score may be shown under a pseudonymous identity |
| `anonymous` | Claim or score should not expose the user’s identity publicly |

The app should distinguish between:

- private evidence;
- reviewer-visible evidence;
- public profile evidence;
- public score explanation.

---

## 12. Audit alignment

Every claim that affects EkoH scores should be traceable.

The system should be able to answer:

- What claim was submitted?
- Who submitted it?
- What evidence supported it?
- Which domains did it affect?
- Who or what verified it?
- What score changed?
- Why did the score change?
- When did it change?
- Was the claim later disputed, expired, or revoked?

The claim layer should therefore connect naturally to:

- score history;
- contextual analysis logs;
- reviewer notes;
- verification records;
- dispute or appeal records where applicable.

---

## 13. Governance alignment

The app should support fair review and reduce gaming.

Important governance concerns include:

- false credentials;
- unverifiable claims;
- duplicate evidence;
- manipulated peer endorsements;
- conflicts of interest;
- stale or expired expertise;
- revoked credentials;
- abusive or unethical conduct;
- attempts to inflate scores through volume rather than quality.

The app should support review states such as:

| State | Meaning |
|---|---|
| Draft | User has not submitted the claim yet |
| Submitted | Claim is awaiting review |
| Under review | Claim is being evaluated |
| Needs more evidence | Reviewer requires additional proof |
| Verified | Claim is accepted |
| Partially verified | Claim is valid but limited in scope or confidence |
| Rejected | Claim is not accepted |
| Disputed | Claim is under appeal or challenge |
| Expired | Claim is no longer current |
| Revoked | Claim was previously accepted but later invalidated |
| Archived | Claim is preserved but inactive |

---

## 14. What this app should do

The app should:

- centralize EkoH-bound expertise and merit evidence through K-Port;
- ingest source-authoritative XKaliber / CertifiKation evidence without re-scoring it;
- collect structured evidence;
- map claims to EkoH expertise domains;
- support internal and external evidence references;
- support peer, expert, admin, and automated validation;
- preserve claim status and review history;
- feed verified signals into EkoH scoring;
- support auditability and transparency;
- respect privacy settings;
- prevent users from directly self-assigning scores.

---

## 15. What this app should not do

The app should not:

- replace `user_expertise_score`;
- replace `user_ethics_score`;
- replace `score_history`;
- create a second reputation system;
- let users directly edit their EkoH score;
- make every external link automatically valid evidence;
- treat popularity as expertise;
- treat all peer endorsements as equally weighted;
- expose private evidence publicly by default;
- decentralize scoring authority into other Konnaxion modules;
- duplicate the competency-assessment authority of XKaliber;
- permit direct module-to-EkoH evidence paths that bypass K-Port.

## 17. Success criteria

The app is aligned with EkoH if:

- claims are centralized in EkoH;
- scores remain centralized in EkoH;
- evidence can come from many sources without fragmenting reputation authority;
- every score-impacting claim is traceable;
- users submit evidence rather than self-awarded scores;
- privacy is respected;
- review and verification states are explicit;
- the claim layer can feed the existing EkoH scoring and audit system.

---

## 18. Summary

The EkoH Expertise Claims App should be understood as the missing bridge between:

```text
user evidence
```

and

```text
EkoH reputation scores
```

It should centralize raw claims and evidence inside the EkoH environment while preserving the existing EkoH score, ethics, privacy, configuration, and audit model.

The guiding principle is:

> Konnaxion produces evidence. EkoH owns reputation.

# K-Port — Architecture Alignment

**Document ID:** `00-k-port-alignment.md`  
**Scope:** K-Port position, ownership, boundaries and integration contracts  
**Category:** application + evidence gateway inside EkoH/Konnaxion

## 1. Purpose

K-Port is the canonical controlled boundary through which evidence intended to affect EkoH reputation is submitted, normalized, qualified and handed to EkoH.

It exists to prevent three failures:

1. evidence producers writing directly into reputation state;
2. K-Port reinterpreting or overwriting source-authoritative facts;
3. EkoH reputation being derived from evidence without traceable provenance, scope and review.

## 2. Architectural classification

```text
kOA Digital Ecosystem
└── Konnaxion                         ecosystem system / platform
    └── EkoH                          internal domain/module
        └── K-Port                    application + evidence gateway
```

K-Port is **not**:

- an ecosystem system peer of Konnaxion;
- a general Konnaxion platform layer;
- an independent reputation system;
- Smart Vote;
- XKaliber;
- CertifiKation;
- an EkoH scoring engine.

A separate K-Port repository is a repository/deployment choice, not an authority boundary that promotes K-Port to an ecosystem system.

## 3. Owner matrix

| State / decision | Authoritative owner |
|---|---|
| XKaliber observed competency and assessment result | XKaliber |
| CertifiKation seal/status | CertifiKation/XKaliber contract |
| Korum deliberation facts | Korum |
| Konsultations consultation/ballot facts | Konsultations |
| Smart Vote reading | Smart Vote |
| K-Port claim/evidence intake | K-Port |
| K-Port evidence qualification/admissibility | K-Port |
| K-Port → EkoH scoring handoff | K-Port |
| EkoH domain taxonomy/context | EkoH |
| EkoH expertise/ethics reputation state | EkoH |
| EkoH score history | EkoH |

The same datum may be referenced by several components, but it has only one logical authoritative owner.

## 4. Core boundary

```text
source fact
≠ evidence copy/reference
≠ K-Port qualification
≠ K-Port admissibility
≠ EkoH score impact
≠ Smart Vote reading
```

K-Port may preserve or reference a source fact. It may not silently mutate the semantics of that source fact.

Example:

```text
XKaliber confirmed_level = 4
```

K-Port may attach:

```text
admissible_for_ekoh = true
mapped_domains = [...]
qualification_reason = ...
```

It must not replace the source fact with a different `confirmed_level`.

## 5. Input classes

### 5.1 User/external evidence

A user may claim experience, credentials, impact, recognition, publications, licenses, project work or other merit and attach supporting evidence.

For these inputs, K-Port owns the review state but not the external institution's underlying truth. Evidence existence, authenticity, identity binding, relevance and freshness are evaluated according to K-Port/EkoH policy.

### 5.2 Source-authoritative internal evidence

Trusted Konnaxion producers may expose structured evidence. The current primary example is XKaliber / CertifiKation inside KonnectED.

K-Port verifies the transport/integrity/provenance/status/scope necessary for admissibility, while respecting the source's own semantic authority.

```text
XKaliber measures
→ CertifiKation attests when applicable
→ K-Port qualifies/routes
→ EkoH scores
```

## 6. Smart Vote and circularity

Smart Vote is a derived-reading system. Its readings may consume EkoH context. A Smart Vote reading therefore must not be treated as canonical evidence to increase the EkoH context that helped produce the reading.

Forbidden default loop:

```text
EkoH context
→ Smart Vote weighting/reading
→ K-Port evidence
→ higher EkoH context
```

If participation or civic conduct is admissible evidence, K-Port references the authoritative source-domain fact directly (for example Korum/Konsultations), not the Smart Vote derived reading.

## 7. K-Port-owned objects

The conceptual K-Port surface is:

```text
ExpertiseClaim
├── ClaimDomain
├── ClaimEvidence
├── ClaimMetric
├── ClaimValidation
└── ScoringHandoff
```

### `ExpertiseClaim`

A structured business-domain claim submitted to K-Port. It is not a Kristal Claim-IR object or assertion.

### `ClaimEvidence`

A stored evidence item or reference, including provenance, source status, visibility and integrity/audit material when available.

### `ClaimDomain`

A K-Port mapping into EkoH's domain catalogue. The source can propose a domain; K-Port may confirm/correct the mapping under policy.

### `ClaimValidation`

A K-Port review result. The word `validation` is local to this application unless an explicit external validation contract is referenced.

### `ScoringHandoff`

The traceable package K-Port sends to EkoH. It records what K-Port qualified and why. It does not own the resulting EkoH score.

## 8. Status separation

K-Port must keep these dimensions distinct:

```text
source_status
claim_review_status
admissibility_status
handoff_status
EkoH_processing/status reference
```

Examples:

- a source record can be `active` while K-Port marks it `not_admissible` for a specific EkoH domain;
- a claim can be `verified` while EkoH produces `no_score_change`;
- an evidence source can later become `revoked`, which requires K-Port to update admissibility and request EkoH re-evaluation without directly editing EkoH scores.

## 9. K-Port → EkoH contract

K-Port sends an explicit handoff/candidate, not an internal-table mutation.

The handoff should carry:

- subject identity reference;
- K-Port claim and evidence references;
- source producer/type/id/version;
- source status and integrity/audit references;
- K-Port review and admissibility state;
- confirmed domain mapping;
- evidence reliability/quality metadata;
- consent/visibility constraints;
- reviewer/decision references;
- correlation/idempotency identifier;
- contract version and timestamp.

EkoH remains free to accept, reject, defer or assign no reputation impact under its own scoring policy.

EkoH returns a receipt/result reference. K-Port retains the reference for traceability but does not mirror EkoH's authoritative score as a writable local field.

## 10. Revocation and correction

A source correction or revocation flows in the same direction as the original evidence:

```text
source correction/revocation
→ K-Port updates source/admissibility state
→ K-Port emits re-evaluation handoff
→ EkoH owns any reputation correction
```

K-Port must not correct EkoH reputation directly.

## 11. Privacy boundary

K-Port handles potentially sensitive evidence. It must separate:

- source evidence;
- K-Port review notes;
- public claim summary;
- EkoH scoring handoff;
- public EkoH profile/score explanation.

A score or public summary does not imply that raw evidence is public.

K-Port should minimize copied sensitive data and prefer stable references when the source can remain authoritative and retrievable under policy.

## 12. Cross-system terminology

The following terms are intentionally scoped:

```text
K-Port ExpertiseClaim
≠ Kristal assertion
≠ Kristal Claim-IR

K-Port verified
≠ universal truth
≠ Kristal validation
≠ institutional recognition

K-Port admissible
≠ EkoH score increase

EkoH reputation signal
≠ Smart Vote ballot
≠ Smart Vote reading
```

## 13. Conformance rules

A conforming K-Port implementation must satisfy all of the following:

1. K-Port is implemented as an application/gateway inside the EkoH/Konnaxion boundary.
2. Source-authoritative facts retain their source owner and provenance.
3. K-Port qualification/admissibility is separate from source validity.
4. K-Port never assigns or directly writes EkoH reputation as its own authority.
5. EkoH scoring is invoked through an explicit handoff/interface.
6. Smart Vote derived readings do not feed back as canonical EkoH expertise evidence.
7. Claim/evidence/review/admissibility/handoff states remain separable.
8. Revocation/correction is traceable and results in EkoH re-evaluation, not direct K-Port score mutation.
9. Privacy and consent constraints travel with evidence and handoff references.
10. Retries of a scoring handoff are idempotent or explicitly reconciled.

## 14. Canonical statement

> **Source systems own facts. K-Port qualifies evidence. EkoH owns reputation. Smart Vote derives readings without becoming an evidence feedback loop.**

# EkoH Expertise Claims App — Concept and Scope

**Document ID:** `01-expertise-claims-concept-and-scope.md`  
**Scope:** Product concept, purpose, boundaries, and terminology  
**Status:** Draft  
**Intended audience:** Product, governance, architecture, UX, and development teams  

---

## 1. Purpose

This document defines the concept and scope of the **EkoH Expertise Claims App**.

The app exists to let users submit structured evidence about their expertise, merit, experience, impact, recognition, and trustworthiness.

It does not calculate reputation by itself.  
It does not replace EkoH.  
It does not allow users to self-award expertise.

Its purpose is to collect, organize, verify, and route expertise-related claims into the EkoH scoring environment.

---

## 2. Product concept

The Expertise Claims App is a centralized EkoH intake layer for mark-of-merit evidence.

It lets a user say:

> “Here is something I have done, learned, earned, built, published, taught, proven, or been recognized for. Here is the evidence. Please evaluate it as part of my EkoH profile.”

The app transforms unstructured proof into structured claims that EkoH can understand.

A claim may support:

- domain expertise;
- practical experience;
- measurable impact;
- peer recognition;
- knowledge dissemination;
- ethical trustworthiness.

---

## 3. Core idea

The app is based on a simple distinction:

```text
Evidence is submitted by the user.
Validity is assessed by verification.
Scores are produced by EkoH.
```

The user can submit evidence.  
The system can organize and verify it.  
Reviewers or automated services can assess it.  
EkoH decides how it affects expertise and ethics scores.

---

## 4. Problem being solved

EkoH already centralizes user expertise scores, ethics scores, score history, privacy, and scoring configuration.

However, there is a missing upstream product layer:

```text
Where does a user submit the evidence that justifies an EkoH score?
```

Without this app, Konnaxion may have evidence scattered across modules, external links, uploads, projects, and user profiles.

The Expertise Claims App solves this by creating a single EkoH-centered place where users can submit claims and proof before scoring.

---

## 5. What is an expertise claim?

An **expertise claim** is a structured user-submitted statement that may support a user’s EkoH profile.

Examples:

- “I have a certification in solar energy systems.”
- “I worked for eight years as a civil engineer.”
- “I created an open-source water-filtration prototype.”
- “My project reduced energy use by 22%.”
- “I published a peer-reviewed article.”
- “I mentored 40 learners in this subject.”
- “A recognized expert endorsed my contribution.”
- “I have verified my professional identity.”
- “I have a strong conduct history in community deliberation.”

A claim is not automatically true.  
A claim is not automatically scored.  
A claim becomes useful only when supported by evidence and verification.

---

## 6. What is a mark-of-merit claim?

A **mark-of-merit claim** is an expertise claim that maps to one of EkoH’s recognized merit dimensions.

Recommended canonical dimensions:

| Merit dimension | Meaning |
|---|---|
| Theoretical knowledge and qualifications | Formal and structured knowledge, such as degrees, certifications, licenses, research, or patents |
| Practical experience | Hands-on work, professional roles, field work, applied projects, or direct practice |
| Measurable impact | Quantified outcomes, real-world results, adoption, beneficiaries, savings, or public-good effects |
| Peer recognition | Endorsements, reviews, citations, expert validation, or community recognition |
| Knowledge dissemination | Teaching, mentoring, tutorials, documentation, publications, or open educational resources |
| Ethical integrity | Conduct, transparency, honesty, respect, responsibility, and alignment with platform values |

These dimensions should define the top-level structure of the app.

---

## 7. What is evidence?

**Evidence** is the proof or support attached to a claim.

Evidence may be internal to Konnaxion or external.

Examples of evidence include:

- uploaded certificate;
- certificate ID;
- institutional verification link;
- degree record;
- license number;
- publication DOI;
- patent reference;
- project link;
- project report;
- code repository;
- portfolio item;
- tutorial;
- documentation;
- impact report;
- endorsement;
- expert review;
- peer validation;
- moderation or conduct record;
- identity verification;
- external professional profile.

Evidence should be treated according to its reliability.

A public link is not the same as institutional verification.  
A self-attested statement is not the same as expert validation.

# K-Port — Concept and Scope

**Document ID:** `01-k-port-concept-and-scope.md`  
**Scope:** Product concept, purpose, boundaries, and terminology  
**Status:** Current product/architecture specification  
**Intended audience:** Product, governance, architecture, UX, and development teams  

---

## 1. Purpose

This document defines the concept and scope of the **K-Port**.

The app exists to let users submit structured evidence about their expertise, merit, experience, impact, recognition, and trustworthiness.

It does not calculate reputation by itself.  
It does not replace EkoH.  
It does not allow users to self-award expertise.

Its purpose is to collect, organize, verify, and route expertise-related claims into the EkoH scoring environment.

---

## Architectural position

K-Port is an **application + evidence gateway inside the EkoH boundary of Konnaxion**. It is not a peer ecosystem system and it is not a second reputation authority.

```text
Konnaxion
└── EkoH
    └── K-Port
```

The product may be developed in its own repository while remaining inside this architectural boundary.

## 2. Product concept

K-Port is a centralized EkoH intake layer for mark-of-merit evidence.

It lets a user say:

> “Here is something I have done, learned, earned, built, published, taught, proven, or been recognized for. Here is the evidence. Please evaluate it as part of my EkoH profile.”

The app transforms unstructured proof into structured claims that EkoH can understand.

A claim may support:

- domain expertise;
- practical experience;
- measurable impact;
- peer recognition;
- knowledge dissemination;
- ethical trustworthiness.

---

## 3. Core idea

The app is based on a simple distinction:

```text
Evidence is submitted by the user.
Validity is assessed by verification.
Scores are produced by EkoH.
```

The user can submit evidence.  
The system can organize and verify it.  
Reviewers or automated services can assess it.  
EkoH decides how it affects expertise and ethics scores.

---

## 4. Problem being solved

EkoH already centralizes user expertise scores, ethics scores, score history, privacy, and scoring configuration.

However, there is a missing upstream product layer:

```text
Where does a user submit the evidence that justifies an EkoH score?
```

Without this app, Konnaxion may have evidence scattered across modules, external links, uploads, projects, and user profiles.

K-Port solves this by creating a single EkoH-centered place where users can submit claims and proof before scoring.

## 5. What is an expertise claim?

> **Terminology boundary:** `ExpertiseClaim` is a K-Port business-domain intake record. It is not a Kristal assertion or Claim-IR object, and K-Port `verified` status does not imply universal truth or external epistemic validation.


An **expertise claim** is a structured user-submitted statement that may support a user’s EkoH profile.

Examples:

- “I have a certification in solar energy systems.”
- “I worked for eight years as a civil engineer.”
- “I created an open-source water-filtration prototype.”
- “My project reduced energy use by 22%.”
- “I published a peer-reviewed article.”
- “I mentored 40 learners in this subject.”
- “A recognized expert endorsed my contribution.”
- “I have verified my professional identity.”
- “I have a strong conduct history in community deliberation.”

A claim is not automatically true.  
A claim is not automatically scored.  
A claim becomes useful only when supported by evidence and verification.

---

## 6. What is a mark-of-merit claim?

A **mark-of-merit claim** is an expertise claim that maps to one of EkoH’s recognized merit dimensions.

Recommended canonical dimensions:

| Merit dimension | Meaning |
|---|---|
| Theoretical knowledge and qualifications | Formal and structured knowledge, such as degrees, certifications, licenses, research, or patents |
| Practical experience | Hands-on work, professional roles, field work, applied projects, or direct practice |
| Measurable impact | Quantified outcomes, real-world results, adoption, beneficiaries, savings, or public-good effects |
| Peer recognition | Endorsements, reviews, citations, expert validation, or community recognition |
| Knowledge dissemination | Teaching, mentoring, tutorials, documentation, publications, or open educational resources |
| Ethical integrity | Conduct, transparency, honesty, respect, responsibility, and alignment with platform values |

These dimensions should define the top-level structure of the app.

- license number;
- publication DOI;
- patent reference;

- portfolio item;
- tutorial;
- documentation;
- impact report;
- endorsement;
- expert review;
- peer validation;
- moderation or conduct record;
- identity verification;
- external professional profile.

Evidence should be treated according to its reliability.

## 1. Purpose

This document describes the conceptual model for the **EkoH Expertise Claims App**.

The goal is to create a shared language for:

- expertise claims;
- mark-of-merit evidence;
- domain mapping;
- impact metrics;
- peer or expert validation;
- verification status;
- scoring handoff to EkoH.

This document should guide product design, UX, and future database/API design.

## 2. Model principle

The model should follow this principle:

```text
Claims are not scores.
Evidence is not automatically valid.
Validation turns claims into score signals.
EkoH remains the scoring authority.
```

The Expertise Claims App should collect and organize evidence.

EkoH should decide how verified evidence affects:

- user expertise scores;
- ethics scores;
- score history;
- contextual analysis logs;
- privacy-controlled profile display.

## 3. High-level model

Recommended conceptual structure:

```text
ExpertiseClaim
├── ClaimDomain
├── ClaimEvidence
├── ClaimMetric
├── ClaimValidation
└── ScoreApplication
```

Each object has a distinct purpose.

| Object | Purpose |
|---|---|
| `ExpertiseClaim` | The main user-submitted statement of expertise or merit |
| `ClaimDomain` | Links the claim to one or more EkoH expertise domains |
| `ClaimEvidence` | Stores or references proof supporting the claim |
| `ClaimMetric` | Captures measurable impact attached to the claim |
| `ClaimValidation` | Records peer, expert, admin, or automated validation |
| `ScoreApplication` | Links a verified claim to a later EkoH score change |

---

## 4. ExpertiseClaim

An **ExpertiseClaim** is the central object.

It represents a user’s structured statement that they have expertise, merit, experience, recognition, impact, or ethical credibility relevant to EkoH.

Examples:

- “I completed this certification.”
- “I worked in this domain for five years.”
- “I built this project.”
- “I published this paper.”
- “I mentored learners in this field.”
- “I received expert validation.”
- “This project produced measurable public benefit.”
- “This conduct record supports my ethical trustworthiness.”

### 4.1 Core information

A claim should capture:

| Field concept | Meaning |
|---|---|
| Claim owner | The user submitting the claim |
| Title | Short human-readable name |
| Description | Explanation of the claim |
| Merit dimension | Which EkoH merit dimension it supports |
| Evidence type | What kind of evidence is being submitted |
| Claim status | Draft, submitted, under review, verified, rejected, etc. |
| Source | Internal Konnaxion source or external source |
| Privacy preference | Public, pseudonym, or anonymous |
| Review notes | Explanation from reviewers or the system |

## 11. ScoreApplication

A **ScoreApplication** links a verified claim to a later EkoH score update.

It answers:

```text
Which verified claim changed which EkoH score, and why?
```

This object is important for traceability.

### 11.1 Score application concepts

A ScoreApplication should capture:

| Field concept | Meaning |
|---|---|
| Source claim | The verified claim used as input |
| Affected user | The user whose score changed |
| Affected domain | The expertise category affected |
| Previous score | Score before application |
| New score | Score after application |
| Score history reference | Link to EkoH audit trail |
| Applied by | Reviewer, system, or scoring service |
| Applied date | When the score change happened |
| Calculation explanation | Human-readable or machine-readable rationale |

### 11.2 Why this matters

Without a score application link, EkoH may know that a score changed but not have a clean path back to the exact claim and evidence that caused the change.

This object makes the bridge auditable.

## 12. Claim status model

The app should support a clear claim lifecycle.

| Status | Meaning |
|---|---|
| Draft | User started the claim but has not submitted it |
| Submitted | User submitted the claim for review |
| Under review | Claim is actively being reviewed |
| Needs more evidence | Reviewers need additional proof |
| Verified | Claim is accepted |
| Partially verified | Claim is accepted only in part |
| Rejected | Claim is not accepted |
| Disputed | Claim is under challenge or appeal |
| Expired | Claim is no longer current |
| Revoked | Previously accepted claim was invalidated |
| Archived | Claim is inactive but preserved |

The status should apply to the claim overall.

Evidence items, metrics, and validations may also have their own verification states.

---

## 13. Relationship between claim status and score impact

Not every claim affects a score.

Recommended relationship:

| Claim status | Score impact |
|---|---|
| Draft | No score impact |
| Submitted | No score impact |
| Under review | No score impact |
| Needs more evidence | No score impact |
| Verified | Eligible for scoring |
| Partially verified | Eligible for limited scoring |
| Rejected | No score impact |
| Disputed | Score impact paused or reviewed |
| Expired | Score may decay or be removed |
| Revoked | Score impact should be reversed or corrected |
| Archived | No new score impact |

This prevents unverified claims from inflating EkoH reputation.

---

## 14. Privacy model

Claims and evidence should support privacy controls.

Recommended visibility levels:

| Visibility | Meaning |
|---|---|
| Private | Visible only to the claimant and authorized reviewers |
| Reviewer-visible | Visible to validation/review roles |
| Pseudonymous | Publicly visible without direct identity exposure |
| Public | Publicly visible with the user’s identity |
| Score-summary only | Claim details hidden, but score explanation may reference a generalized reason |

The app should distinguish:

- evidence privacy;
- claim summary privacy;
- score explanation privacy;
- validator comment privacy.

A user may allow their score to be public while keeping sensitive proof private.

---

## 15. Internal versus external references

The app should support both internal Konnaxion references and external references.

### 15.1 Internal references

Examples:

- XKaliber Caliber Profile or assessment result;
- CertifiKation seal;
- Konnaxion project;
- KonnectED portfolio item;
- KnowledgeResource;
- Ethikos contribution;
- Empower vote;
- project review;
- moderation/conduct record.

An internal reference should identify the source module and object. For source-authoritative evidence, it should also preserve version, status, validity and an audit or integrity reference.

For XKaliber / CertifiKation evidence, fields such as confirmed level and assessment confidence are **source facts**, not values that K-Port recalculates. K-Port may add separate admissibility, mapping and evidence-reliability metadata without overwriting the source facts.

Conceptually:

```text
source_module
source_type
source_id
source_version
source_status
source_verified_at
source_valid_until
source_audit_reference
```

### 15.2 External references

Examples:

- university degree;
- professional license;
- DOI;
- patent;
- GitHub repository;
- ORCID;
- open badge;
- institutional registry;
- external portfolio.

An external reference should identify the source, URL or ID, issuer, and verification method.

## 16. Trust and anti-gaming attributes

The model should support anti-gaming review without making the first version too complex.

Useful concepts include:

| Concept | Purpose |
|---|---|
| Duplicate detection | Prevent the same evidence from being submitted many times |
| Conflict of interest | Identify biased validators or reviewers |
| Evidence reliability | Distinguish weak and strong proof |
| Validator relevance | Ensure validators are credible in the relevant domain |
| Claim freshness | Reduce reliance on outdated evidence |
| Revocation | Correct claims that become invalid |
| Dispute state | Allow challenge and review |
| Source metadata | Preserve context for future audits |
| Reviewer notes | Explain decisions |

These should support trust without turning the app into a heavy compliance system at MVP stage.

## 17. Minimal conceptual model for MVP

The MVP should include:

```text
ExpertiseClaim
├── ClaimDomain
└── ClaimEvidence
```

Recommended MVP capabilities:

- create claim;
- select merit dimension;
- select evidence type;
- map to one or more domains;
- attach evidence by file or URL;
- submit for review;
- change claim status;
- add reviewer note;
- mark verified or rejected;
- ingest source-authoritative Konnaxion evidence, including XKaliber / CertifiKation;
- hand admissible verified evidence to EkoH scoring.

This is enough to close the central claim/evidence gap.

## 22. Summary

The Expertise Claims App should use a clean model:

```text
Claim
Evidence
Domain
Metric
Validation
Score application
```

The most important object is the claim.

The most important rule is that a claim does not equal a score.

The model should help EkoH answer:

```text
What was claimed?
What evidence supports it?
Which domain does it affect?
Who or what verified it?
Did it change a score?
Can we audit the change later?
```

The guiding statement is:

> Structured claims make expertise auditable before it becomes influence.

# K-Port — Claim and Evidence Model

**Document ID:** `02-k-port-claim-evidence-model.md`  
**Scope:** Conceptual data model for expertise claims, evidence, domains, metrics, validation, and score handoff  
**Status:** Current product/architecture specification  
**Intended audience:** Product, architecture, UX, governance, and development teams

## 1. Purpose

This document describes the conceptual model for the **K-Port**.

It defines the main objects the app should understand, without going too deep into implementation details.

The goal is to create a shared language for K-Port-owned intake and qualification state:

- expertise claims;
- mark-of-merit evidence;
- domain mapping;
- impact metrics;
- peer or expert validation;
- verification status;
- scoring handoff to EkoH.

This document should guide product design, UX, and future database/API design.

---

## 2. Model principle

The model should follow this principle:

```text
Claims are not scores.
Evidence is not automatically valid.
Validation turns claims into score signals.
EkoH remains the scoring authority.
```

K-Port should collect and organize evidence.

EkoH should decide how verified evidence affects:

- user expertise scores;
- ethics scores;
- score history;
- contextual analysis logs;
- privacy-controlled profile display.

---

## 3. High-level model

Recommended conceptual structure:

```text
ExpertiseClaim
├── ClaimDomain
├── ClaimEvidence
├── ClaimMetric
├── ClaimValidation
└── ScoringHandoff
```

| Object | Purpose |
|---|---|

| `ClaimEvidence` | Stores or references proof supporting the claim |
| `ClaimMetric` | Captures measurable impact attached to the claim |
| `ClaimValidation` | Records peer, expert, admin, or automated validation |
| `ScoringHandoff` | Carries qualified evidence to EkoH for an independent scoring decision |

## 11. ScoringHandoff

A **ScoringHandoff** records the evidence package that K-Port submits to EkoH for scoring consideration.

It answers:

```text
What qualified evidence did K-Port send to EkoH, for which subject/domains, under which provenance, consent and review state?
```

It deliberately does **not** represent the score mutation itself. EkoH owns score calculation, score state and score history.

### 11.1 Scoring handoff concepts

A `ScoringHandoff` should capture:

| Field concept | Meaning |
|---|---|
| Subject | User/person the evidence concerns |
| Source claim | K-Port claim used as input |
| Evidence references | Qualified evidence included in the handoff |
| Source references | Producer/type/id/version/status for source-authoritative evidence |
| Domain mappings | Confirmed EkoH domains and relevance |
| Admissibility result | K-Port decision and reason |
| Qualification metadata | Evidence reliability/confidence/review metadata in K-Port scope |
| Consent/visibility | Constraints EkoH must preserve |
| Correlation/idempotency ID | Stable identifier for retries/reconciliation |
| Handoff version/time | Contract version and issuance time |
| EkoH receipt/reference | Optional downstream processing reference returned by EkoH |

K-Port must not treat `previous_score`, `new_score` or a local writable score field as authoritative fields of this object. Those belong to EkoH and may only be referenced through an EkoH-owned receipt/history record.

### 11.2 Why this matters

Separating the handoff from the score mutation preserves ownership:

```text
K-Port qualification
→ ScoringHandoff
→ EkoH scoring decision
→ EkoH score/history
```

A verified claim can therefore produce no score change without creating a contradiction in K-Port state.

| Under review | No score impact |
| Needs more evidence | No score impact |
| Verified | May be eligible for EkoH handoff under policy |
| Partially verified | Eligible for limited scoring |
| Rejected | No score impact |
| Disputed | Score impact paused or reviewed |
| Expired | Score may decay or be removed |
| Revoked | Score impact should be reversed or corrected |
| Archived | No new score impact |

This prevents unverified claims from inflating EkoH reputation.

---

## 14. Privacy model

Claims and evidence should support privacy controls.

Recommended visibility levels:

| Visibility | Meaning |
|---|---|
| Private | Visible only to the claimant and authorized reviewers |
| Reviewer-visible | Visible to validation/review roles |
| Pseudonymous | Publicly visible without direct identity exposure |
| Public | Publicly visible with the user’s identity |
| Score-summary only | Claim details hidden, but score explanation may reference a generalized reason |

The app should distinguish:

- evidence privacy;
- claim summary privacy;
- score explanation privacy;
- validator comment privacy.

A user may allow their score to be public while keeping sensitive proof private.

---

## 15. Internal versus external references

The app should support both internal Konnaxion references and external references.

### 15.1 Internal references

Examples:

- XKaliber Caliber Profile or assessment result;
- CertifiKation seal;
- Konnaxion project;
- KonnectED portfolio item;
- KnowledgeResource;
- Ethikos contribution;
- Empower vote;
- project review;
- moderation/conduct record.

An internal reference should identify the source module and object. For source-authoritative evidence, it should also preserve version, status, validity and an audit or integrity reference.

For XKaliber / CertifiKation evidence, fields such as confirmed level and assessment confidence are **source facts**, not values that K-Port recalculates. K-Port may add separate admissibility, mapping and evidence-reliability metadata without overwriting the source facts.

Conceptually:

```text
source_producer
source_type
source_id
source_version
source_status
source_verified_at
source_valid_until
source_audit_reference
```

### 15.2 External references

Examples:

- university degree;
- professional license;
- DOI;
- patent;
- GitHub repository;
- ORCID;
- open badge;
- institutional registry;
- external portfolio.

An external reference should identify the source, URL or ID, issuer, and verification method.

---

## 16. Trust and anti-gaming attributes

The model should support anti-gaming review without making the first version too complex.

Useful concepts include:

| Concept | Purpose |
|---|---|
| Duplicate detection | Prevent the same evidence from being submitted many times |
| Conflict of interest | Identify biased validators or reviewers |
| Evidence reliability | Distinguish weak and strong proof |
| Validator relevance | Ensure validators are credible in the relevant domain |
| Claim freshness | Reduce reliance on outdated evidence |
| Revocation | Correct claims that become invalid |
| Dispute state | Allow challenge and review |
| Source metadata | Preserve context for future audits |
| Reviewer notes | Explain decisions |

These should support trust without turning the app into a heavy compliance system at MVP stage.

- change claim status;
- add reviewer note;
- mark verified or rejected;

This is enough to close the central claim/evidence gap.

# EkoH Expertise Claims App — Intake Form

**Document ID:** `03-expertise-claim-intake-form.md`  
**Scope:** User-facing intake form for submitting expertise and mark-of-merit claims  
**Status:** Draft  
**Intended audience:** Product, UX, governance, architecture, and development teams  

---

## 1. Purpose

This document describes the user-facing intake form for the **EkoH Expertise Claims App**.

The form is the bridge between:

```text
user evidence
```

and

```text
EkoH expertise and ethics scoring
```

The form should help users submit structured, reviewable claims without letting them directly assign themselves EkoH scores.

The purpose of the form is to collect:

- what the user is claiming;
- which EkoH merit dimension the claim supports;
- which expertise domain or domains are involved;
- what evidence supports the claim;
- whether there is measurable impact;
- who can validate it;
- how private the claim should be;
- whether there are conflicts of interest.

---

## 2. Design principle

The form should be simple for users but structured enough for EkoH.

Recommended principle:

```text
Ask users for proof, not scores.
```

The user should never be asked:

```text
What EkoH score should this give you?
```

Instead, the form should ask:

```text
What did you do, earn, build, teach, publish, prove, or receive recognition for?
What evidence supports it?
Which domain does it belong to?
Who can verify it?
```

---

## 3. Form outcome

A submitted form should create one central EkoH expertise claim.

Conceptually:

```text
ExpertiseClaim
├── selected merit dimension
├── selected evidence type
├── one or more expertise domains
├── one or more evidence items
├── optional impact metrics
├── optional validators
├── privacy settings
└── review status
```

The form should produce a reviewable claim, not an immediate score change.

---

## 4. Recommended form flow

A clear first version can use seven steps:

```text
1. Claim type
2. Claim details
3. Expertise domains
4. Evidence
5. Impact
6. Validation
7. Privacy and submission
```

The form may be implemented as a wizard, a single page with sections, or a hybrid.

For users, a wizard may be clearer.

For reviewers and power users, a single-page expert mode may be useful later.

---

## 5. Step 1 — Claim type

This step helps the user classify the claim.

### 5.1 User prompt

```text
What kind of merit are you submitting?
```

### 5.2 Merit dimension selector

The user selects one primary merit dimension.

| Option | User-facing explanation |
|---|---|
| Theoretical knowledge and qualifications | I have formal knowledge, credentials, research, patents, or training |
| Practical experience | I have hands-on experience, work history, or project participation |
| Measurable impact | I can show real-world results or quantified outcomes |
| Peer recognition | Others have endorsed, reviewed, cited, or recognized my work |
| Knowledge dissemination | I have taught, mentored, published, documented, or shared knowledge |
| Ethical integrity | I have trust, transparency, conduct, or responsibility signals |

### 5.3 Evidence type selector

After selecting a merit dimension, the user selects an evidence type.

Examples:

| Merit dimension | Suggested evidence types |
|---|---|
| Theoretical knowledge and qualifications | Degree, certification, license, course completion, publication, patent |
| Practical experience | Project, professional experience, portfolio item, field work, implementation |
| Measurable impact | Impact report, adoption data, beneficiary count, environmental metric, financial metric |
| Peer recognition | Peer endorsement, expert review, citation, award, community validation |
| Knowledge dissemination | Teaching, mentoring, tutorial, documentation, open resource, curriculum |
| Ethical integrity | Identity verification, conduct record, transparency declaration, moderation history |

The user should also have an `Other` option, but it should require an explanation.

---

## 6. Step 2 — Claim details

This step captures the human-readable claim.

### 6.1 User prompt

```text
Describe what you are submitting.
```

### 6.2 Recommended fields

| Field | Required | Notes |
|---|---:|---|
| Claim title | Yes | Short title, easy to scan |
| Description | Yes | Explain what the user did, earned, built, taught, or proved |
| Role | Conditional | Useful for projects, employment, publications, and team work |
| Organization / issuer | Conditional | School, employer, institution, project, publisher, certifier |
| Start date | Conditional | For experience, projects, mentoring, teaching, or long-term work |
| End date | Conditional | Optional if ongoing |
| Issue date | Conditional | For credentials, certifications, licenses, awards |
| Expiry date | Conditional | For expiring credentials |
| External reference | Optional | DOI, certificate ID, patent number, license number, ORCID, repository, badge ID |
| Source URL | Optional | Public proof link |
| Notes | Optional | Extra context |

### 6.3 Suggested help text

```text
Describe the claim clearly enough that another person can understand what you are asking EkoH to consider.
```

### 6.4 Avoided field

Do not include:

```text
Requested EkoH score
```

A self-assessed level may be allowed only as context.

If included, label it carefully:

```text
Self-assessed level, for context only
```

---

## 7. Step 3 — Expertise domains

This step maps the claim to EkoH expertise categories.

### 7.1 User prompt

```text
Which expertise domain or domains does this claim belong to?
```

### 7.2 Domain selector

The selector should use EkoH’s canonical expertise category catalogue.

The user should be able to:

- search domains;
- browse domain hierarchy;
- select more than one domain;
- mark the main domain;
- optionally add relevance weights;
- let AI or reviewers suggest corrections later.

### 7.3 Recommended fields

| Field | Required | Notes |
|---|---:|---|
| Primary domain | Yes | Main domain affected by the claim |
| Additional domains | Optional | For interdisciplinary claims |
| Relevance | Optional | Simple values such as High / Medium / Low are enough for MVP |
| Domain rationale | Optional | Why this domain applies |

### 7.4 User-facing guidance

```text
Choose the field where this evidence best demonstrates expertise. If it applies to multiple fields, add them in order of relevance.
```

### 7.5 Reviewer note

Domain mapping should be reviewable.

A reviewer or AI-assisted classifier may later:

- confirm the user’s selection;
- add a missing domain;
- remove a weak domain;
- adjust relevance;
- request clarification.

---

## 8. Step 4 — Evidence

This is the most important section.

### 8.1 User prompt

```text
Add proof that supports your claim.
```

### 8.2 Evidence input types

The form should support:

| Evidence input | Description |
|---|---|
| File upload | PDF, image, document, certificate, report |
| URL | Public webpage, project page, profile, registry, repository |
| Identifier | DOI, patent number, certificate ID, badge ID, license number |
| Internal Konnaxion reference | XKaliber result, CertifiKation seal, project, portfolio item, resource, debate contribution, Empower signal |
| Text explanation | Used only as supporting context, not as primary proof |

### 8.3 Recommended fields per evidence item

| Field | Required | Notes |
|---|---:|---|
| Evidence title | Yes | Human-readable label |
| Evidence kind | Yes | File, URL, certificate ID, DOI, internal reference, etc. |
| Evidence location / value | Yes | Upload, link, ID, or reference |
| Description | Optional | Explain why this evidence matters |
| Issuer / source | Conditional | Institution, person, project, platform, registry |
| Date issued | Conditional | Useful for credentials and awards |
| Expiry date | Conditional | Useful for licenses and certifications |
| Visibility | Yes | Private, reviewer-visible, public summary, public |
| Verification method | Optional | Self-attested, peer, expert, institution, registry, API, source-authoritative |
| Notes | Optional | Extra details |

### 8.4 Multiple evidence items

The form should allow multiple evidence items per claim.

Example:

```text
Claim: Open-source water filter prototype

Evidence:
- project report PDF
- public repository
- deployment photos
- partner organization letter
- impact report
```

### 8.5 Evidence reliability reminder

The form should inform users:

```text
Stronger evidence can make review easier. Official, verifiable, or third-party evidence is stronger than self-attested evidence.
```

---

## 9. Step 5 — Impact

This step is optional for most claims but important for measurable impact.

### 9.1 User prompt

```text
Did this claim produce measurable results?
```

### 9.2 Recommended fields

| Field | Required | Notes |
|---|---:|---|
| Impact metric | Conditional | What was measured |
| Value | Conditional | Numeric value |
| Unit | Conditional | People, dollars, kg CO2, hours, downloads, citations, etc. |
| Time period | Optional | When the impact occurred |
| Source | Optional | Where the number comes from |
| Evidence link | Optional | Report or proof supporting the metric |
| Notes | Optional | Context or explanation |

### 9.3 Example metric options

| Metric | Example unit |
|---|---|
| People helped | people |
| Learners trained | people |
| Patients treated | people |
| Funds raised | CAD / USD / EUR |
| Emissions reduced | kg CO2e |
| Energy saved | kWh |
| Water saved | liters |
| Downloads | count |
| Citations | count |
| Implementations | count |
| Hours contributed | hours |
| Cost reduced | currency |

### 9.4 User-facing guidance

```text
Use measurable results only when you can explain where the number comes from.
```

The form should discourage vague inflation such as:

```text
Changed thousands of lives
```

unless supported by evidence.

---

## 10. Step 6 — Validation

This step lets the user request peer or expert validation.

### 10.1 User prompt

```text
Who can help validate this claim?
```

### 10.2 Validator types

Possible validator roles:

| Validator type | Description |
|---|---|
| Peer | Someone familiar with the work |
| Expert | Someone with relevant domain expertise |
| Mentor | Someone who supervised or trained the user |
| Collaborator | Someone who worked on the project |
| Institution | Organization that issued or can confirm the evidence |
| Admin / reviewer | Konnaxion governance or review role |
| Automated verification | Registry, API, or external check |

### 10.3 Recommended fields

| Field | Required | Notes |
|---|---:|---|
| Validator name | Conditional | For invited people |
| Validator email or Konnaxion ID | Conditional | Needed for invitation |
| Validator role | Yes | Peer, expert, mentor, collaborator, institution, etc. |
| Relationship to claimant | Yes | How they know the claim |
| Relevant domain | Optional | Domain where they can validate |
| Conflict of interest | Yes | User declares whether there is a possible conflict |
| Message to validator | Optional | Short explanation or request |

### 10.4 Validation warning

The form should clarify:

```text
Validation from someone with relevant expertise may carry more weight than generic support.
```

This keeps peer recognition distinct from popularity.

---

## 11. Step 7 — Privacy and submission

This final step lets the user review, choose visibility, and submit.

### 11.1 User prompt

```text
Review your claim before submitting it.
```

### 11.2 Privacy selector

Recommended options:

| Privacy option | Meaning |
|---|---|
| Private | Visible only to you and authorized reviewers |
| Reviewer-visible | Visible to people reviewing or validating the claim |
| Pseudonymous public summary | Claim may be summarized publicly without exposing your identity |
| Public summary | Claim summary may be publicly linked to your profile |
| Public evidence | Evidence itself may be publicly visible |

### 11.3 Submission checklist

Before submission, the form should ask the user to confirm:

- the information is accurate to the best of their knowledge;
- they have the right to share the evidence;
- private or sensitive data has been handled carefully;
- conflicts of interest have been disclosed;
- they understand the claim may be reviewed, rejected, disputed, or expire;
- they understand submission does not guarantee a score increase.

### 11.4 Final button

Recommended button labels:

```text
Submit claim for review
```

or

```text
Submit evidence to K-Port
```

Avoid:

```text
Increase my score
```

- domain mapping.

### 12.6 Peer recognition

- endorser or reviewer;

### 12.7 Knowledge dissemination

Show:

### 12.8 Ethical integrity

Show:

- reviewer visibility controls.

## 17. Form validation rules

After selecting a merit dimension, the user selects an evidence type.

| Merit dimension | Suggested evidence types |

# K-Port — Verification and EkoH Handoff

**Document ID:** `04-k-port-verification-and-ekoh-handoff.md`  
**Scope:** Verification workflow and handoff from expertise claims to EkoH scoring  
**Status:** Current product/architecture specification  
**Intended audience:** Product, governance, architecture, UX, and development teams  

---

## 1. Purpose

This document describes what happens after a user submits an expertise or mark-of-merit claim.

It explains how the claim should move through verification and how verified claim signals should be handed off to EkoH scoring.

K-Port should not calculate final reputation by itself.

Its role is to prepare structured, verified inputs for EkoH and to act as the **canonical evidence gateway** for EkoH-bound expertise evidence, including source-authoritative XKaliber / CertifiKation results.

---

## 2. Core principle

The workflow should follow this principle:

```text
Submission does not equal verification.
Source verification does not equal re-assessment.
Verification does not equal automatic score increase.
Scoring remains an EkoH responsibility.
```

A claim may be valid but minor.  
A claim may be real but irrelevant to the selected domain.  
A claim may be relevant but weakly evidenced.  
A claim may be strong enough to affect one domain but not another.

The verification and scoring handoff must preserve these distinctions.

---

## 3. High-level flow

Recommended flow:

```text
User-submitted claim OR source-authoritative module evidence
        ↓
K-Port intake / import
        ↓
Evidence is verified at the appropriate boundary
        ↓
Domain mapping is confirmed or corrected
        ↓
Evidence is accepted, partially accepted, rejected, expired, revoked, or disputed
        ↓
Admissible signal is handed to EkoH scoring
        ↓
EkoH updates score tables where appropriate
        ↓
Score change is recorded in audit history
        ↓
User is notified of outcome
```

The app should make this flow understandable to both users and reviewers.

---

## 4. Verification goals

Verification should answer five questions:

```text
1. Is the evidence real?
2. Does the evidence support the claim?
3. Is the claim mapped to the correct expertise domain?
4. How strong or reliable is the evidence?
5. Should this claim become a scoring signal?
```

Verification should not simply answer:

```text
Should the user get points?
```

That decision belongs to the EkoH scoring process.

---

## 5. Claim lifecycle

A claim should move through explicit states.

| Status | Meaning |
|---|---|
| Draft | User has started the claim but has not submitted it |
| Submitted | Claim is ready for review |
| Under review | Reviewer, validator, or system is evaluating the claim |
| Needs more evidence | Claim cannot proceed without additional proof |
| Verified | Claim is accepted as valid evidence |
| Partially verified | Claim is valid only in part, or only for some domains |
| Rejected | Claim is not accepted |
| Disputed | Claim is being challenged or appealed |
| Expired | Claim is no longer current |
| Revoked | Previously accepted claim has been invalidated |
| Archived | Claim is inactive but preserved |

Only verified or partially verified claims should be eligible for score handoff.

---

## 6. Review types

The system should support several verification methods.

| Review type | Use case |
|---|---|
| Self-attestation | User provides claim and evidence without external confirmation |
| Peer validation | Another user confirms the claim or contribution |
| Expert validation | A domain-relevant expert reviews the claim |
| Admin review | Governance or moderation role reviews the claim |
| Institution verification | Issuing institution confirms the evidence |
| Registry verification | Public or official registry confirms the record |
| API verification | External service confirms a credential, publication, identity, or record |
| AI-assisted review | AI helps classify, summarize, or flag evidence |
| Imported Konnaxion evidence | Evidence comes from an existing Konnaxion object |
| Source-authoritative verification | Trusted source module proves provenance, status and integrity of a measurement it owns, such as XKaliber / CertifiKation |

These methods may be combined.

Example:

```text
A certificate may be user-submitted, registry-verified, and then admin-reviewed.
```

---

## 6A. Source-authoritative evidence: XKaliber / CertifiKation

XKaliber is authoritative for the competency performance it measures. CertifiKation is authoritative for the seal it issues from a confirmed result. When K-Port receives this evidence, it should not reproduce the assessment workflow.

K-Port should verify:

- provenance and integrity of the source record;
- the stable source ID and version;
- binding to the correct Konnaxion user;
- active, expired, disputed, corrected or revoked status;
- evaluation and validity dates;
- domain / competency scope;
- consent and visibility constraints;
- duplication or supersession;
- mapping into the canonical EkoH domain catalogue.

K-Port should preserve as source-authoritative facts:

- confirmed competency level;
- XKaliber assessment confidence or margin;
- assessment rule / item-set version references;
- source correction and revocation state.

K-Port may add its own **evidence reliability**, **EkoH domain relevance**, **admissibility status**, and review notes. These must be stored separately from the source assessment result.

If the user contests the measured competency, the dispute routes back to XKaliber / CertifiKation. If the dispute concerns K-Port mapping or admissibility, it stays in K-Port. If it concerns reputation impact, it routes to EkoH.

---

## 7. Verification decisions

A reviewer or verification process should be able to make nuanced decisions.

| Decision | Meaning |
|---|---|
| Approve | Evidence supports the claim |
| Partially approve | Evidence supports part of the claim |
| Reject | Evidence does not support the claim |
| Request more evidence | Claim is plausible but insufficiently supported |
| Correct domain | Claim is valid but mapped to the wrong domain |
| Mark duplicate | Claim repeats an existing verified claim |
| Mark expired | Claim was once valid but is no longer current |
| Escalate | Claim needs expert, admin, or governance review |
| Flag concern | Claim may involve fraud, conflict of interest, manipulation, or abuse |

The system should avoid forcing every review into a simple yes/no result.

---

## 8. Domain verification

A claim’s domain mapping must be reviewable.

A reviewer may:

- confirm the selected domain;
- add a missing domain;
- remove an irrelevant domain;
- adjust domain relevance;
- mark the claim as interdisciplinary;
- request clarification;
- reject domain relevance while still accepting the evidence.

Example:

```text
A publication on AI ethics may affect both ICT and ethics/policy domains.
```

Example:

```text
A generic management certificate may not strongly affect a technical engineering domain.
```

The handoff to EkoH should include the final verified domain mapping, not only the user’s original selection.

---

## 9. Evidence verification

Evidence should be checked for both existence and relevance.

A reviewer should ask:

```text
Does this evidence exist?
Is it authentic?
Is it connected to the claimant?
Does it support the described claim?
Is it current?
Is it complete?
Is it strong enough for the claimed merit dimension?
```

Examples:

| Evidence | Verification concern |
|---|---|
| Certificate PDF | Is it issued by a legitimate institution? Is the claimant named? Is it expired? |
| Publication | Is the claimant an author? What role did they have? Is the DOI valid? |
| Project link | Did the user contribute? What role did they play? |
| Impact report | Are the numbers sourced and plausible? |
| Peer endorsement | Is the validator credible and free of conflict? |
| Portfolio item | Is it original work? Is it relevant to the selected domain? |

---

## 10. Impact verification

Measurable impact claims require extra care.

A reviewer should check:

- the metric name;
- the numeric value;
- the unit;
- the measurement period;
- the source of the number;
- whether the metric can be independently confirmed;
- whether the claimant’s contribution caused or contributed to the impact;
- whether the impact is relevant to the selected domain.

Example:

```text
“Reduced emissions by 10,000 kg CO2e” should include the calculation source, measurement period, and project context.
```

Impact claims may be accepted at different confidence levels.

---

## 11. Peer and expert validation

Peer recognition is an important mark of merit, but not all validation should carry equal weight.

The validation process should consider:

- validator identity;
- validator expertise domain;
- validator relationship to the claimant;
- possible conflict of interest;
- quality of the validator’s comment;
- whether the validator reviewed the evidence;
- whether the validator has relevant EkoH credibility.

A peer endorsement should not be treated the same as expert validation unless the peer has relevant domain standing.

---

## 12. AI-assisted review

AI may support verification, but should not be treated as the final authority for sensitive or high-impact decisions.

AI can help with:

- summarizing evidence;
- detecting missing fields;
- suggesting expertise domains;
- identifying duplicate claims;
- flagging suspicious patterns;
- extracting dates, issuers, or identifiers;
- comparing claim text to evidence text;
- producing reviewer summaries.

AI should not silently approve claims.

AI-assisted decisions should be explainable and reviewable.

---

## 13. Score handoff eligibility

A claim should be eligible for scoring only when:

- it has been submitted;
- it has at least one evidence item;
- it has at least one confirmed domain;
- it has a verification result;
- its verification status is `verified` or `partially_verified`;
- it has not been revoked;
- it is not currently disputed in a way that blocks scoring;
- privacy and consent requirements are respected.

Rejected, draft, and incomplete claims should not affect EkoH scores.

---

## 14. Handoff package

A handoff is a versioned boundary object/command, not a direct mutation of EkoH internal tables. Retries must be idempotent or explicitly reconciled, and EkoH should return a processing receipt/reference that K-Port can retain for audit correlation.

When a claim is ready for EkoH scoring, the app should pass a structured handoff package.

Conceptually, the package should include:

| Handoff element | Purpose |
|---|---|
| Claim ID | Traceability |
| User ID | User whose EkoH profile may be affected |
| Merit dimension | What kind of merit is involved |
| Evidence type | What kind of proof supports the claim |
| Verified domains | Which expertise categories are affected |
| Domain relevance | Relative strength per domain |
| Verification status | Verified or partially verified |
| Verification method | Peer, expert, admin, institution, registry, source-authoritative, AI-assisted, etc. |
| Source authority | Which module or issuer is authoritative for the underlying result, if applicable |
| Source object ID / version | Stable trace to the originating evidence object |
| Source status / validity | Active, expired, disputed, corrected, revoked, and validity window |
| Evidence reliability | How trustworthy the proof is as an EkoH input |
| Impact metrics | Structured measurable outcomes, if any |
| Reviewer notes | Explanation for human audit |
| Confidence level | How strongly the system trusts the claim |
| Privacy constraints | What can be shown or referenced |
| Source references | Evidence IDs, URLs, internal object references |
| Date context | When the claim occurred, was issued, expires, or was verified |

This package lets EkoH score the claim without losing context.

---

## 15. Relationship to existing EkoH score objects

Verified claims should feed existing EkoH score and audit objects.

| Existing EkoH object | Relationship |
|---|---|
| `expertise_category` | Defines the domains affected by the claim |
| `user_expertise_score` | May be updated after scoring |
| `user_ethics_score` | May be updated if the claim affects trust or ethics |
| `score_configuration` | Provides scoring parameters |
| `context_analysis_log` | Stores explainable contextual or AI-assisted adjustments |
| `score_history` | Records score changes |
| `confidentiality_setting` | Controls public identity and visibility |

K-Port should hand off structured evidence signals through an explicit EkoH scoring/domain interface. It should not write these EkoH-owned objects as if they were K-Port state.

It should not replace them.

---

## 16. Scoring responsibilities

K-Port should be responsible for:

- collecting claims;
- ingesting evidence from internal and external sources;
- preserving source-authoritative facts without re-scoring them;
- collecting domain mappings;
- collecting metrics;
- collecting validation results;
- preserving review states;
- preparing scoring handoff data;
- preserving traceability;
- preventing EkoH-bound evidence from bypassing the canonical K-Port gateway.

EkoH scoring should be responsible for:

- deciding score impact;
- applying scoring parameters;
- updating user expertise scores;
- updating ethics scores if relevant;
- applying domain relevance;
- applying evidence reliability;
- applying confidence and quality considerations;
- recording score history;

# EkoH Expertise Claims App — Verification and Scoring Handoff

**Document ID:** `04-verification-and-scoring-handoff.md`  
**Scope:** Verification workflow and handoff from expertise claims to EkoH scoring  
**Status:** Draft  
**Intended audience:** Product, governance, architecture, UX, and development teams  

---

## 1. Purpose

This document describes what happens after a user submits an expertise or mark-of-merit claim.

It explains how the claim should move through verification and how verified claim signals should be handed off to EkoH scoring.

The Expertise Claims App should not calculate final reputation by itself.

Its role is to prepare structured, verified inputs for EkoH and to act as the **canonical evidence gateway** for EkoH-bound expertise evidence, including source-authoritative XKaliber / CertifiKation results.

---

## 2. Core principle

The workflow should follow this principle:

```text
Submission does not equal verification.
Source verification does not equal re-assessment.
Verification does not equal automatic score increase.
Scoring remains an EkoH responsibility.
```

A claim may be valid but minor.  
A claim may be real but irrelevant to the selected domain.  
A claim may be relevant but weakly evidenced.  
A claim may be strong enough to affect one domain but not another.

The verification and scoring handoff must preserve these distinctions.

---

## 3. High-level flow

Recommended flow:

```text
User-submitted claim OR source-authoritative module evidence
        ↓
K-Port intake / import
        ↓
Evidence is verified at the appropriate boundary
        ↓
Domain mapping is confirmed or corrected
        ↓
Evidence is accepted, partially accepted, rejected, expired, revoked, or disputed
        ↓
Admissible signal is handed to EkoH scoring
        ↓
EkoH updates score tables where appropriate
        ↓
Score change is recorded in audit history
        ↓
User is notified of outcome
```

The app should make this flow understandable to both users and reviewers.

---

## 4. Verification goals

Verification should answer five questions:

```text
1. Is the evidence real?
2. Does the evidence support the claim?
3. Is the claim mapped to the correct expertise domain?
4. How strong or reliable is the evidence?
5. Should this claim become a scoring signal?
```

Verification should not simply answer:

```text
Should the user get points?
```

That decision belongs to the EkoH scoring process.

---

## 5. Claim lifecycle

A claim should move through explicit states.

| Status | Meaning |
|---|---|
| Draft | User has started the claim but has not submitted it |
| Submitted | Claim is ready for review |
| Under review | Reviewer, validator, or system is evaluating the claim |
| Needs more evidence | Claim cannot proceed without additional proof |
| Verified | Claim is accepted as valid evidence |
| Partially verified | Claim is valid only in part, or only for some domains |
| Rejected | Claim is not accepted |
| Disputed | Claim is being challenged or appealed |
| Expired | Claim is no longer current |
| Revoked | Previously accepted claim has been invalidated |
| Archived | Claim is inactive but preserved |

Only verified or partially verified claims should be eligible for score handoff.

---

## 6. Review types

The system should support several verification methods.

| Review type | Use case |
|---|---|
| Self-attestation | User provides claim and evidence without external confirmation |
| Peer validation | Another user confirms the claim or contribution |
| Expert validation | A domain-relevant expert reviews the claim |
| Admin review | Governance or moderation role reviews the claim |
| Institution verification | Issuing institution confirms the evidence |
| Registry verification | Public or official registry confirms the record |
| API verification | External service confirms a credential, publication, identity, or record |
| AI-assisted review | AI helps classify, summarize, or flag evidence |
| Imported Konnaxion evidence | Evidence comes from an existing Konnaxion object |
| Source-authoritative verification | Trusted source module proves provenance, status and integrity of a measurement it owns, such as XKaliber / CertifiKation |

These methods may be combined.

Example:

```text
A certificate may be user-submitted, registry-verified, and then admin-reviewed.
```

---

## 6A. Source-authoritative evidence: XKaliber / CertifiKation

XKaliber is authoritative for the competency performance it measures. CertifiKation is authoritative for the seal it issues from a confirmed result. When K-Port receives this evidence, it should not reproduce the assessment workflow.

K-Port should verify:

- provenance and integrity of the source record;
- the stable source ID and version;
- binding to the correct Konnaxion user;
- active, expired, disputed, corrected or revoked status;
- evaluation and validity dates;
- domain / competency scope;
- consent and visibility constraints;
- duplication or supersession;
- mapping into the canonical EkoH domain catalogue.

K-Port should preserve as source-authoritative facts:

- confirmed competency level;
- XKaliber assessment confidence or margin;
- assessment rule / item-set version references;
- source correction and revocation state.

K-Port may add its own **evidence reliability**, **EkoH domain relevance**, **admissibility status**, and review notes. These must be stored separately from the source assessment result.

If the user contests the measured competency, the dispute routes back to XKaliber / CertifiKation. If the dispute concerns K-Port mapping or admissibility, it stays in K-Port. If it concerns reputation impact, it routes to EkoH.

---

## 7. Verification decisions

A reviewer or verification process should be able to make nuanced decisions.

| Decision | Meaning |
|---|---|
| Approve | Evidence supports the claim |
| Partially approve | Evidence supports part of the claim |
| Reject | Evidence does not support the claim |
| Request more evidence | Claim is plausible but insufficiently supported |
| Correct domain | Claim is valid but mapped to the wrong domain |
| Mark duplicate | Claim repeats an existing verified claim |
| Mark expired | Claim was once valid but is no longer current |
| Escalate | Claim needs expert, admin, or governance review |
| Flag concern | Claim may involve fraud, conflict of interest, manipulation, or abuse |

The system should avoid forcing every review into a simple yes/no result.

---

## 8. Domain verification

A claim’s domain mapping must be reviewable.

A reviewer may:

- confirm the selected domain;
- add a missing domain;
- remove an irrelevant domain;
- adjust domain relevance;
- mark the claim as interdisciplinary;
- request clarification;
- reject domain relevance while still accepting the evidence.

Example:

```text
A publication on AI ethics may affect both ICT and ethics/policy domains.
```

Example:

```text
A generic management certificate may not strongly affect a technical engineering domain.
```

The handoff to EkoH should include the final verified domain mapping, not only the user’s original selection.

---

## 9. Evidence verification

Evidence should be checked for both existence and relevance.

A reviewer should ask:

```text
Does this evidence exist?
Is it authentic?
Is it connected to the claimant?
Does it support the described claim?
Is it current?
Is it complete?
Is it strong enough for the claimed merit dimension?
```

Examples:

| Evidence | Verification concern |
|---|---|
| Certificate PDF | Is it issued by a legitimate institution? Is the claimant named? Is it expired? |
| Publication | Is the claimant an author? What role did they have? Is the DOI valid? |
| Project link | Did the user contribute? What role did they play? |
| Impact report | Are the numbers sourced and plausible? |
| Peer endorsement | Is the validator credible and free of conflict? |
| Portfolio item | Is it original work? Is it relevant to the selected domain? |

---

## 10. Impact verification

Measurable impact claims require extra care.

A reviewer should check:

- the metric name;
- the numeric value;
- the unit;
- the measurement period;
- the source of the number;
- whether the metric can be independently confirmed;
- whether the claimant’s contribution caused or contributed to the impact;
- whether the impact is relevant to the selected domain.

Example:

```text
“Reduced emissions by 10,000 kg CO2e” should include the calculation source, measurement period, and project context.
```

Impact claims may be accepted at different confidence levels.

---

## 11. Peer and expert validation

Peer recognition is an important mark of merit, but not all validation should carry equal weight.

The validation process should consider:

- validator identity;
- validator expertise domain;
- validator relationship to the claimant;
- possible conflict of interest;
- quality of the validator’s comment;
- whether the validator reviewed the evidence;
- whether the validator has relevant EkoH credibility.

A peer endorsement should not be treated the same as expert validation unless the peer has relevant domain standing.

---

## 12. AI-assisted review

AI may support verification, but should not be treated as the final authority for sensitive or high-impact decisions.

AI can help with:

- summarizing evidence;
- detecting missing fields;
- suggesting expertise domains;
- identifying duplicate claims;
- flagging suspicious patterns;
- extracting dates, issuers, or identifiers;
- comparing claim text to evidence text;
- producing reviewer summaries.

AI should not silently approve claims.

AI-assisted decisions should be explainable and reviewable.

---

## 13. Score handoff eligibility

A claim should be eligible for scoring only when:

- it has been submitted;
- it has at least one evidence item;
- it has at least one confirmed domain;
- it has a verification result;
- its verification status is `verified` or `partially_verified`;
- it has not been revoked;
- it is not currently disputed in a way that blocks scoring;
- privacy and consent requirements are respected.

Rejected, draft, and incomplete claims should not affect EkoH scores.

---

## 14. Handoff package

When a claim is ready for EkoH scoring, the app should pass a structured handoff package.

Conceptually, the package should include:

| Handoff element | Purpose |
|---|---|
| Claim ID | Traceability |
| User ID | User whose EkoH profile may be affected |
| Merit dimension | What kind of merit is involved |
| Evidence type | What kind of proof supports the claim |
| Verified domains | Which expertise categories are affected |
| Domain relevance | Relative strength per domain |
| Verification status | Verified or partially verified |
| Verification method | Peer, expert, admin, institution, registry, source-authoritative, AI-assisted, etc. |
| Source authority | Which module or issuer is authoritative for the underlying result, if applicable |
| Source object ID / version | Stable trace to the originating evidence object |
| Source status / validity | Active, expired, disputed, corrected, revoked, and validity window |
| Evidence reliability | How trustworthy the proof is as an EkoH input |
| Impact metrics | Structured measurable outcomes, if any |
| Reviewer notes | Explanation for human audit |
| Confidence level | How strongly the system trusts the claim |
| Privacy constraints | What can be shown or referenced |
| Source references | Evidence IDs, URLs, internal object references |
| Date context | When the claim occurred, was issued, expires, or was verified |

This package lets EkoH score the claim without losing context.

---

## 15. Relationship to existing EkoH score objects

Verified claims should feed existing EkoH score and audit objects.

| Existing EkoH object | Relationship |
|---|---|
| `expertise_category` | Defines the domains affected by the claim |
| `user_expertise_score` | May be updated after scoring |
| `user_ethics_score` | May be updated if the claim affects trust or ethics |
| `score_configuration` | Provides scoring parameters |
| `context_analysis_log` | Stores explainable contextual or AI-assisted adjustments |
| `score_history` | Records score changes |
| `confidentiality_setting` | Controls public identity and visibility |

The claim app should hand off structured signals to these existing EkoH objects.

It should not replace them.

---

K-Port / the Expertise Claims App should be responsible for:

- collecting claims;
- ingesting evidence from internal and external sources;
- preserving source-authoritative facts without re-scoring them;
- collecting domain mappings;
- collecting metrics;
- collecting validation results;
- preserving review states;
- preparing scoring handoff data;
- preserving traceability;
- preventing EkoH-bound evidence from bypassing the canonical K-Port gateway.

EkoH scoring should be responsible for:

- deciding score impact;
- applying scoring parameters;
- updating user expertise scores;
- updating ethics scores if relevant;
- applying domain relevance;
- applying evidence reliability;
- applying confidence and quality considerations;
- recording score history;
- recording contextual analysis.

# EkoH Expertise Claims App — Governance, Privacy, and Audit

**Document ID:** `05-governance-privacy-and-audit.md`  
**Scope:** Governance rules, privacy expectations, auditability, dispute handling, and trust controls for the EkoH Expertise Claims App  
**Status:** Draft  
**Intended audience:** Governance, product, architecture, UX, privacy, moderation, and development teams  

---

## 1. Purpose

This document describes the governance, privacy, and audit expectations for the **EkoH Expertise Claims App**.

The app handles sensitive evidence that may influence reputation, expertise recognition, ethics weighting, and voting influence inside Konnaxion.

Because of that, it must be designed around:

- fairness;
- transparency;
- privacy;
- traceability;
- anti-gaming;
- appealability;
- accountable score changes.

The app should strengthen trust in EkoH, not simply collect more data.

---

## 2. Core governance principle

The governing principle is:

```text
No claim or module-produced evidence should influence EkoH without passing through K-Port with traceable provenance, appropriate review, and accountability.
```

A user may submit a claim.  
A validator may support it.  
A reviewer may approve it.  
EkoH may convert it into a score signal.  

Every step should be explainable.

---

## 3. Why governance matters

Expertise claims can affect:

- a user’s domain reputation;
- their visibility as an expert;
- the weight of their participation in Smart Vote;
- trust in their recommendations;
- credibility of Konnaxion outcomes;
- public perception of fairness.

Poor governance could create:

- fake expertise;
- unfair score inflation;
- popularity contests;
- hidden bias;
- privacy leaks;
- manipulation by organized groups;
- distrust in EkoH.

The claim layer must therefore be treated as a trust-sensitive system.

---

## 4. Governance goals

The app should support the following goals.

| Goal | Meaning |
|---|---|
| Evidence-based merit | Claims must be supported by proof |
| Domain relevance | Claims must affect only relevant domains |
| Fair review | Similar claims should be treated consistently |
| Privacy protection | Sensitive evidence should not be exposed unnecessarily |
| Traceability | Score-impacting claims must be auditable |
| Anti-gaming | Manipulation and fraud should be detectable |
| Appealability | Users should be able to challenge decisions |
| Revocability | Invalidated claims should be correctable |
| Proportionality | Minor claims should not produce exaggerated influence |
| Inclusion | Nontraditional expertise should be recognized when evidenced |

---

## 5. Privacy model

The app should separate several privacy layers.

A user may want their expertise recognized without making all supporting documents public.

### 5.1 Privacy layers

| Layer | Description |
|---|---|
| Claim metadata | Title, merit dimension, domain, status |
| Claim description | User’s explanation of the claim |
| Evidence | Files, URLs, IDs, certificates, reports, references |
| Review notes | Reviewer comments and internal assessments |
| Validator comments | Peer or expert validation statements |
| Score explanation | Public or private reason why a score changed |
| Identity link | Whether the claim is tied publicly to the user’s real identity |

These layers should not all have the same visibility by default.

---

## 6. Recommended visibility levels

The app should support visibility choices that align with EkoH privacy expectations.

| Visibility level | Meaning |
|---|---|
| Private | Visible only to the claimant and authorized reviewers |
| Reviewer-visible | Visible to reviewers and validators involved in the claim |
| Pseudonymous | Publicly visible without direct real-identity exposure |
| Public summary | Claim summary may be publicly associated with the user |
| Public evidence | Evidence itself may be publicly visible |
| Score explanation only | The score impact may be summarized without exposing full evidence |

A common and safe default is:

```text
Claim summary: private until verified
Evidence: reviewer-visible only
Score explanation: summarized, privacy-aware
```

---

## 7. Sensitive evidence

Some evidence may be especially sensitive.

Examples:

- identity documents;
- diplomas with personal information;
- employment records;
- professional licenses;
- medical or legal documents;
- letters of recommendation;
- moderation history;
- conflict-of-interest declarations;
- private project reports;
- validator comments;
- internal review notes.

The app should avoid exposing sensitive evidence publicly unless the user explicitly chooses to do so and the platform permits it.

---

## 8. Consent and user control

Users should understand what they are submitting.

Before submission, the app should ask the user to confirm:

- the information is accurate to the best of their knowledge;
- they have the right to submit the evidence;
- the evidence does not expose another person without permission;
- they understand the claim may be reviewed;
- they understand submission does not guarantee a score increase;
- they understand verified claims may affect their EkoH profile;
- they understand false claims may be rejected, revoked, or affect trust.

The app should make privacy choices clear before submission.

---

## 9. Reviewer access

Reviewer access should follow the principle of least privilege.

Reviewers should see only what they need to evaluate the claim.

Recommended access distinctions:

| Role | Access |
|---|---|
| Claimant | Own claims, own evidence, public/review outcomes |
| Peer validator | Claim summary and selected evidence needed for validation |
| Expert reviewer | Claim, domains, evidence, metrics, validation context |
| Admin reviewer | Full claim context, governance notes, dispute information |
| Public user | Only public or privacy-safe summaries |
| K-Port evidence process | Source records, provenance, admissibility, mapping, status and required audit references |
| EkoH scoring process | Structured admissible signals and required audit references; no need for raw assessment data |

Private evidence should not be exposed to unrelated users.

---

## 10. Audit model

Every score-impacting claim should be auditable.

The audit trail should answer:

```text
Who submitted the claim?
What was claimed?
What evidence supported it?
If evidence came from XKaliber / CertifiKation, what source object, version, status and audit reference produced it?
Which domains were affected?
Who validated or reviewed it?
What decision was made?
When was it made?
Was the claim sent to scoring?
Did EkoH update a score?
What score changed?
Why did it change?
Was the claim later disputed, expired, or revoked?
```

The app should preserve this chain even if the public view hides sensitive details.

---

## 11. Public transparency versus private evidence

Transparency does not mean exposing everything.

A public explanation may say:

```text
This user's expertise in environmental engineering increased after a verified project contribution was reviewed and accepted.
```

It does not necessarily need to show:

- the full project report;
- private partner letters;
- reviewer notes;
- identity documents;
- raw moderation data.

The app should support privacy-aware transparency.

---

## 12. Reviewer accountability

Review decisions should include:

- reviewer identity or reviewer role;
- decision;
- date;
- rationale;
- domains confirmed or rejected;
- evidence considered;
- confidence level;
- conflicts of interest, if any;
- whether the claim was escalated.

This prevents arbitrary or unexplained decisions.

For public-facing views, reviewer identity may be hidden or generalized depending on governance policy.

- a family member;
- a business partner;
- a project collaborator;
- an employer or employee;
- a competitor;
- financially connected to the claimant;
- involved in a dispute with the claimant.


| Pattern | Description |
|---|---|

| Duplicate claims | Same evidence submitted repeatedly to inflate score |
| Circular endorsements | Users endorse each other to inflate reputation |
| Low-quality claim flooding | Many weak claims submitted to overwhelm review |
| Domain stretching | Claim mapped to unrelated high-value domains |
| Impact inflation | Metrics exaggerated or unsupported |
| Validator bias | Validators with conflicts endorse claims |
| Sockpuppet validation | Fake accounts validate claims |
| Plagiarism | User claims someone else’s work |
| Expired evidence | Outdated or revoked credentials presented as active |
| Popularity substitution | Generic likes treated as expertise |

| Network bias | Favoring users with access to prestigious validators |
| Popularity bias | Mistaking visibility for expertise |
| Geographic bias | Overvaluing evidence formats common in some countries |

## 1. Purpose

This document describes the governance, privacy, and audit expectations for the **K-Port**.

K-Port handles sensitive evidence that may influence EkoH reputation and expertise/ethics context. Downstream systems such as Smart Vote may consume governed EkoH context, but K-Port itself does not assign voting influence.

Because of that, it must be designed around:

- fairness;
- transparency;
- privacy;
- traceability;
- anti-gaming;
- appealability;
- accountable score changes.

The app should strengthen trust in EkoH, not simply collect more data.

---

## 2. Core governance principle

The governing principle is:

```text
No claim or evidence-producer output should influence EkoH reputation without passing through K-Port with traceable provenance, appropriate qualification, and accountability.
```

A user may submit a claim.  
A validator may support it.  
A reviewer may approve it.  
EkoH may convert it into a score signal.  

Every step should be explainable.

K-Port must also prevent circular reputation amplification: a Smart Vote derived reading must not be reintroduced as canonical K-Port evidence for the EkoH context that helped produce that reading.

---

## 3. Why governance matters

Expertise claims can affect:

- a user’s domain reputation;
- their visibility as an expert;
- downstream contextual readings that may consume governed EkoH context;
- trust in their recommendations;
- credibility of Konnaxion outcomes;
- public perception of fairness.

Poor governance could create:

- fake expertise;
- unfair score inflation;
- popularity contests;
- hidden bias;
- privacy leaks;
- manipulation by organized groups;
- distrust in EkoH.

The claim layer must therefore be treated as a trust-sensitive system.

The app should support the following goals.

| Goal | Meaning |
|---|---|
| Evidence-based merit | Claims must be supported by proof |

| Fair review | Similar claims should be treated consistently |
| Privacy protection | Sensitive evidence should not be exposed unnecessarily |
| Traceability | Score-impacting claims must be auditable |
| Anti-gaming | Manipulation and fraud should be detectable |
| Appealability | Users should be able to challenge decisions |
| Revocability | Invalidated claims should be correctable |
| Proportionality | Minor claims should not produce exaggerated influence |
| Inclusion | Nontraditional expertise should be recognized when evidenced |

| Identity link | Whether the claim is tied publicly to the user’s real identity |

These layers should not all have the same visibility by default.

| Visibility level | Meaning |
|---|---|
| Private | Visible only to the claimant and authorized reviewers |
| Reviewer-visible | Visible to reviewers and validators involved in the claim |
| Pseudonymous | Publicly visible without direct real-identity exposure |
| Public summary | Claim summary may be publicly associated with the user |
| Public evidence | Evidence itself may be publicly visible |
| Score explanation only | The score impact may be summarized without exposing full evidence |

A common and safe default is:

```text
Claim summary: private until verified
Evidence: reviewer-visible only
Score explanation: summarized, privacy-aware
```

The app should make privacy choices clear before submission.

Reviewers should see only what they need to evaluate the claim.

Recommended access distinctions:

| Role | Access |
|---|---|

The app should preserve this chain even if the public view hides sensitive details.

# K-Port

**K-Port** is the canonical evidence-intake and qualification application for EkoH inside Konnaxion.

Architecturally, K-Port is an **application + evidence gateway inside the EkoH boundary**. It is not an ecosystem system peer of Konnaxion, and it is not an independent reputation engine.

Its job is to receive user-submitted or source-produced evidence, preserve provenance and source authority, determine whether that evidence is admissible for EkoH, and prepare an explicit scoring handoff. **EkoH alone owns the resulting domain-bounded reputation state.**

## Architectural position

```text
Konnaxion                         ecosystem system / platform
└── EkoH                          internal domain/module; reputation owner
    └── K-Port                    application + evidence gateway
```

The repository may be separate for product and delivery reasons; repository location does not make K-Port an independent architectural system.

## Core ownership rule

```text
Source producer owns source facts
→ K-Port owns evidence intake, qualification and admissibility
→ EkoH owns reputation/scoring state
```

Examples:

```text
XKaliber measures competency
→ CertifiKation attests a confirmed result when applicable
→ K-Port verifies provenance/status/scope/consent and qualifies evidence
→ EkoH calculates domain-bounded reputation impact
```

K-Port must never recalculate an XKaliber result, redefine a CertifiKation seal, or directly assign an EkoH score.

## Inputs

K-Port accepts two broad classes of input.

### User or externally supplied evidence

Examples include:

- degrees and certifications;
- professional licenses;
- employment or project evidence;
- publications and patents;
- measurable impact reports;
- peer or institutional attestations;
- teaching and mentoring records;
- public-interest contributions;
- privacy-appropriate ethical or conduct evidence.

These inputs require review because K-Port does not automatically trust a user assertion or an external URL merely because it exists.

### Source-authoritative Konnaxion evidence

Some evidence is already produced by another bounded process. The main current example is XKaliber / CertifiKation evidence inside KonnectED.

For source-authoritative evidence K-Port verifies, at minimum:

- source identity and provenance;
- integrity or audit reference when available;
- subject identity binding;
- source version;
- source status, including correction/revocation when applicable;
- domain and competency scope;
- validity period;
- consent and visibility constraints;
- duplicate/supersession state;
- mapping to the canonical EkoH domain catalogue.

K-Port adds its own **admissibility decision** without overwriting source facts.

## Smart Vote boundary

Smart Vote owns derived readings over source participation and contextual lenses. A Smart Vote reading is therefore **not a canonical expertise fact** and must not be fed back into K-Port as a shortcut for increasing EkoH reputation.

When civic participation is relevant as evidence, K-Port references the source-owned event or artifact from its authoritative domain (for example a Korum or Konsultations source record) and evaluates that evidence under explicit policy.

```text
source participation fact
→ optional K-Port qualification
→ EkoH context/reputation
→ optional Smart Vote reading

Smart Vote reading
↛ K-Port evidence shortcut
```

This prevents circular reputation amplification.

## What K-Port owns

K-Port owns the state required to operate its evidence gateway, including:

- expertise/merit claim intake;
- evidence references and evidence metadata;
- provenance records held by the gateway;
- EkoH domain mapping proposed/confirmed for the evidence;
- review and qualification state;
- admissibility decisions;
- consent/visibility metadata relevant to the handoff;
- scoring handoff records;
- audit references for its own decisions.

## What K-Port does not own

K-Port does not own:

- XKaliber assessment results;
- CertifiKation seal semantics or source status;
- Korum deliberation state;
- Konsultations ballot/consultation state;
- Smart Vote readings;
- EkoH expertise scores;
- EkoH ethics scores;
- EkoH scoring policy;
- EkoH score history;
- global Konnaxion identity or authorization state.

Possessing evidence does not transfer ownership of the source fact.

## Claim terminology

`ExpertiseClaim` is a **K-Port business-domain intake object**. It is not a Kristal assertion, Claim-IR object, validation result, or epistemic status.

Likewise, `verified` in the K-Port claim lifecycle means that K-Port's evidence-review requirements were satisfied for its own scope. It does not imply Kristal validation, universal truth, institutional recognition, or authorization outside K-Port/EkoH.

## Claim lifecycle

```text
Draft
→ Submitted
→ Under review
→ Needs more evidence | Verified | Partially verified | Rejected
→ Eligible for EkoH handoff when policy permits
→ Handoff receipt / no-impact / further review
→ Disputed | Expired | Revoked | Archived when applicable
```

Claim review status, source evidence status, K-Port admissibility, and EkoH score state are separate axes and must not be collapsed into one field.

## Core conceptual objects

| Object | Owner | Purpose |
|---|---|---|
| `ExpertiseClaim` | K-Port | User/business-domain claim submitted for evidence review |
| `ClaimDomain` | K-Port | Mapping between the claim/evidence and one or more EkoH domains |
| `ClaimEvidence` | K-Port | Evidence reference plus provenance/visibility metadata |
| `ClaimMetric` | K-Port | Structured measurable impact claimed by the submitter/source |
| `ClaimValidation` | K-Port | Review/qualification result in K-Port's scope |
| `ScoringHandoff` | K-Port | Immutable/traceable package sent to EkoH for scoring consideration |
| EkoH score/history objects | EkoH | Reputation state and the authoritative record of score changes |

`ScoringHandoff` is the K-Port-owned boundary object: K-Port prepares evidence for scoring; **EkoH applies scoring**.

## Handoff contract

A K-Port → EkoH handoff should identify at least:

- subject/user reference;
- K-Port claim/evidence IDs;
- source producer/type/id/version when applicable;
- source status and integrity/audit references;
- K-Port admissibility outcome and reason;
- confirmed EkoH domain mappings;
- evidence reliability/qualification metadata;
- consent and visibility constraints;
- reviewer/decision references appropriate to policy;
- idempotency/correlation identifier;
- handoff timestamp/version.

EkoH returns or exposes a receipt/reference to its own processing. K-Port may retain that reference for traceability, but the resulting score and score history remain EkoH-owned.

## Guiding statement

> **K-Port collects and qualifies proof. EkoH evaluates reputation. Source systems keep ownership of their facts.**
