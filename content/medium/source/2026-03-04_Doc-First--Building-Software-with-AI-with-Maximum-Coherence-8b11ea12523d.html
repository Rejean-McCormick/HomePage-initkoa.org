Doc-First: Building Software with AI with Maximum Coherence

A serious software project quickly outgrows what a single AI chat can hold. Context gets truncated, the session degrades, and eventually you have to start a new conversation. At that point the model is effectively starting from zero. The workflow therefore has to be designed to reconstruct context efficiently, keep direction stable, and make progress despite practical limits (context size, prompt complexity, cumulative scope).

This workflow is built from a small set of concrete mechanisms:

  • Doc-first: an initial exhaustive document that defines the product as it should exist at the end and fixes the inter-file alignment variables — the contracts that keep modules and files coherent with each other.
  • Achievable tasks: work is sliced to the size the AI can reliably handle per prompt.
  • Full-code context: the AI sees the real project via a smart dump of the relevant code.
  • Build, then consolidate: first reach a complete, fully functional prototype (generation + debugging); then clean up and optimize in a controlled way with tests.
  • Post-build understanding: detailed understanding is strengthened after the system exists; the built application becomes the best study object.
  • Human-led debugging when blocked: when the AI loops or stalls, the human has to be able to diagnose and unblock, using the AI as an accelerator.
  • Scale orchestration inside the system (optional): in very large projects, an internal orchestration layer can be required to track many files with multiple degrees of completion (e.g., the Everything Matrix inside Semantik Architect).

1) Doc-first: an injectable, stable reference

The starting point is documentation written before code, oriented toward the final version of the product. It is exhaustive where it matters for alignment: everything that must stay consistent across files and modules.

That includes, for example:

  • module responsibilities and boundaries
  • interface contracts and APIs
  • naming conventions and formats
  • invariants and non-negotiable rules
  • expected behaviors and edge cases
  • system-wide constraints (where applicable)

This is not documentation as a “nice-to-have.” It is the mechanism that makes the project continuous across conversations. When a new chat has to be opened, the doc is what reloads the system’s identity quickly and coherently.

Key nuance: the doc is exhaustive about inter-file contracts, not about every internal detail inside each file. Internal implementation can evolve, but the shared contracts remain stable.

2) Achievable tasks: calibrate to the model’s context limit

Task slicing isn’t a management style — it’s a technical constraint. If a prompt is overloaded (too much code, too many constraints, too many objectives), quality drops: the model will drop elements or make mistakes.

Smaller tasks increase reliability. The trade-off is obvious: smaller tasks require more prompts, which takes longer. The workflow is about finding a workable balance between speed and correctness.

Rule of thumb: up to roughly 800 lines of code, the AI usually handles a file reasonably well. Past that, the file is split into multiple files by responsibility (instead of staying one large file). Then the AI can work file-by-file with far fewer context-related errors, and the codebase becomes easier to maintain.

3) Smart dump: give the AI the real codebase

When the AI only sees snippets, it has to infer what it can’t see. On real projects, that inference creates inconsistency: imagined signatures, ignored conventions, changes that break other parts of the system.

My Smart Dumpd solves this by providing a global view of the relevant code while excluding noise (for example by honoring .gitignore). The AI then reasons from what actually exists: real structures, real dependencies, real interfaces. https://github.com/Rejean-McCormick/tools/tree/main/smart_dumper

4) Build first, then consolidate

During construction, the goal is a complete, fully functional prototype. Effort concentrates on two activities:

  1. producing the code (generate, assemble, integrate)
  2. debugging until the system runs end-to-end

At that stage, code will often be non-optimal: redundancy, temporary structures, uneven style, quick compromises. That is expected while the system is still being assembled.

Once the system is complete and stable, the work changes. Cleanup and optimization become both feasible and efficient because you can finally see:

  • the real end-to-end flows
  • where duplication actually exists
  • which components are central vs peripheral
  • what can be simplified without guessing

Consolidation is done in a controlled way: change something, then ensure all tests still pass after each optimization.

5) Understanding after the build: the system becomes the study object

In a classic workflow, building something you don’t fully understand in detail can look irrational. Here, it’s a consequence of AI-assisted development: during the transitional phase, the AI can handle a portion of local implementation complexity while the overall direction remains anchored in the doc.

After the system runs, understanding becomes much more productive. The AI can help explain the system as it actually exists:

  • map modules and responsibilities
  • explain flows and dependencies
  • surface invariants and fragile points
  • guide targeted improvements

Understanding isn’t skipped — it’s reinforced on top of a real artifact.

6) Why re-running a file through the AI becomes appropriate when it was generated quickly

In traditional development, it’s risky to hand a hard-earned file to an AI and ask it to rewrite it. That file often contains subtle decisions and implicit constraints, and the cost of regression can be high.

When a file was produced quickly with AI assistance, the relationship to refactoring changes. The code is more naturally treated as malleable during early phases: it can be reshaped, clarified, and reorganized — especially once shared contracts are locked by documentation and behavior is protected by tests.

7) Debugging: unblocking remains a human responsibility

A single bug can freeze a project. When the AI loops or fails to resolve an issue, progress depends on human-led diagnosis: isolate the problem, reduce it, identify the cause, choose a direction. The AI accelerates the work, but unblocking requires ownership and decision-making.

8) Scale orchestration: the Everything Matrix inside Semantik Architect

Some projects reach a point where orchestration becomes its own problem: many files must be coordinated, and those files sit at different degrees of completion (e.g., draft → partially implemented → reviewed → expert-validated).

In Semantik Architect, that complexity required an internal orchestration layer: the Everything Matrix. Its purpose is strictly to track the state of all working files and their completion level so the system can be steered coherently. It does not “decide” architecture or implement features. It makes the project’s current state legible, which is essential when the number of moving pieces becomes large.

Conclusion

This workflow makes long, complex AI-assisted projects viable with maximum coherence:

  • doc-first, with exhaustive inter-file alignment contracts
  • task sizing calibrated to context limits (≈800 lines; beyond that, split into files)
  • a smart dump so the AI sees the real codebase
  • build to a complete prototype first, then consolidate with tests
  • deepen understanding after the system exists
  • human-led debugging to unblock hard failures
  • internal orchestration when the system’s scale requires it (Everything Matrix in Semantik Architect)

The goal is straightforward: maintain a stable trajectory toward a coherent final product, even when development spans many conversations and a large codebase.
